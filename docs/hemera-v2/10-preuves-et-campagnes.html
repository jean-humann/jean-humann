2. Un banc jetable, avec les vrais composants

Le bilan JSON compte 33 sondes/gates : 18 passent, 5 échouent et 10 sont non exécutés. La mission 17 a créé un banc Docker local distinct des conteneurs utilisateur. Les ports étaient liés à localhost, les identités et données synthétiques. Aucun cluster client ni configuration de production n’a été touché. Lakekeeper, OpenFGA, PostgreSQL, stockage S3 et serveur Spark Connect ont réellement exécuté les opérations décrites.

Versions du banc : Lakekeeper 0.12.0, OpenFGA 1.8.16, PostgreSQL 16.15, SeaweedFS 4.36, Spark Connect 4.1.2 et Keycloak 26.7.4 comme IdP de référence temporaire. Les images sont épinglées dans les preuves. Le client Spark Python 3.10 est distinct du venv de préflight Python 3.13. SQLGlot 30.12.0 appartient au banc de comparaison ; ne pas le confondre avec 30.21.0 du prototype.

Le chemin PyIceberg → Lakekeeper utilise un token OIDC et le modèle OpenFGA natif. Les lectures/écritures S3 utilisent le remote signing, sans clé de stockage dans ce client. Le serveur Spark emploie un bearer synthétique partagé pour Connect. Ce dernier ne prouve pas l’identité JWT par utilisateur, le token exchange ou son renouvellement. Spark et Keycloak sont uniquement des instruments transitoires de preuve ; ils ne réintègrent pas la cible finale sans JVM.

Le veto WAP supplémentaire conserve le snapshot publié et supprime la ref de stage. La lecture de la même table par PyIceberg et Spark passe ; après ajout de colonne, Spark déjà chargé nécessite REFRESH TABLE pour voir le nouveau schéma.

4. Lecture de staging reproduite malgré le veto logique

Le contrat de confidentialité attendu échoue dans le banc. Un utilisateur synthétique doté d’un droit select sur la table obtient les métadonnées et un GET S3 signé pour les fichiers d’un snapshot WAP non publié. Il lit le payload synthétique avant publication, puis après suppression de la branche en visant l’identifiant historique du snapshot. La référence main reste inchangée.

Le test utilise le remote signing Lakekeeper et ne remet aucune clé S3 au lecteur. Il confirme que limiter les credentials au niveau de la table ne suffit pas à isoler ses snapshots de travail. La suppression de la référence n’efface ni l’historique ni les fichiers déjà référencés. Il ne démontre pas une vulnérabilité sur les déploiements clients, qui n’ont pas été testés ; il réfute l’usage du seul grant de table comme frontière WAP Hemera.

La résolution retenue maintient le stockage de travail privé et sert les données par des composants de confiance qui vérifient l’édition publiée et l’ensemble de ses objets. L’accès natif ne s’ouvre qu’après une preuve équivalente sur métadonnées, manifests, données, deletes et statistiques. Le futur test doit aussi couvrir révocation, anciennes URLs, candidats perdant le CAS et fichiers copiés avant publication. Voir le contrat cible.

Les grants/révocations standards passent sur le banc Lakekeeper/OpenFGA : administrateur 200, anonyme 401, tiers 404, tiers autorisé 200, puis 404 après retrait. Les flux ouverts, caches, credentials distribués et pannes restent à tester.
