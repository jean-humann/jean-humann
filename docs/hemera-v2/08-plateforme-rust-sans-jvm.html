1. Décisions de cible

Hemera v2 conserve Iceberg, Lakekeeper et OpenFGA. Les services Cleyrop ont un cœur métier Rust. Icegres fournit les composants de lecture et d’écriture à qualifier ; Eidos fournit le compilateur sémantique, les objets métier et la préparation des actions. Flows orchestre les exécutions. Un contrat de publication commun fait de l’édition Iceberg estampillée la seule autorité sur les données publiées et les positions d’ingestion.

La cible finale contient zéro JVM. Spark, Trino, Keycloak, Kafka, Strimzi, le writer Java OLake, les plugins et outils d’exploitation Java sortent du périmètre final. Le banc Spark Connect reste un instrument temporaire de comparaison. Python et SQL restent des langages utilisateurs ; TypeScript reste adapté aux interfaces ; des exécutants Go ou C++ peuvent être encapsulés. Cela ne crée pas une seconde autorité de publication.

EL-4 est tranché au niveau architecture. OLake devient un extracteur Go borné. Un writer et un coordinateur Rust contrôlent staging, audits, commit et acquittement. L’intégration technique reste à construire et à prouver. Le repli passe par un journal durable puis une édition brute sous WAP, sans exception d’audit après publication. Voir la décision détaillée.

Cette étude distingue le code observé, le design proposé et les preuves exécutées. Les dix tests du prototype sont verts. Ils ne prouvent ni l’isolation entre clients, ni la concurrence du publisher, ni la parité avec Spark et Trino. Les campagnes du document 10 portent ces preuves et leurs limites. Les composants Rust décrits ci-dessous ne sont pas annoncés comme livrés.

3. Une propriété claire pour chaque service

Le plan de contrôle résout les identités, valide les manifestes, autorise les opérations, planifie les ressources et décide les publications. Le plan de données lit les éditions autorisées, traite les octets et prépare des résultats immuables. Les cœurs Rust portent les règles communes entre API et workers. La cible ne demande pas un microservice pour chaque crate. Réécrire toute l’infrastructure tierce en Rust n’apporte pas de garantie supplémentaire ; Lakekeeper, OpenFGA, PostgreSQL et un IdP qualifié restent des dépendances explicites.

5. Le contrat qui relie tous les services

Le résultat d’un worker est un résultat préparé, jamais un succès de publication. Il identifie le run et sa tentative, le dataset, l’UUID de table, l’environnement, la tête de départ, la branche privée, le snapshot candidat, les schémas, les entrées épinglées et la plage source. Le publisher vérifie l’identité, les audits liés à ce candidat exact, l’autorisation courante, le fencing et les préconditions de commit.

PreparedEdition → AuditDecision → ConditionalPublish → PublicationReceipt → SourceAck

PublicationReceipt proposé :
  dataset_id, table_uuid, environment, edition_id
  expected_head, published_snapshot_id, prepared_snapshot_id
  run_id, attempt, fence, idempotency_key, audit_digest
  origin.system, origin.cursor, origin.state, origin.provenance
  input_editions, manifest_digest, source_epoch

Les noms forment un contrat proposé, à versionner. Les valeurs origin.* sont inscrites dans le summary dès la création du snapshot candidat. La référence ou release autorisée établit sa publication ; un champ ajouté par le writer ne suffit pas. Le fast-forward ne réécrit pas rétroactivement ce summary. Une propriété globale de table peut changer pendant un stage et ne satisfait pas l’invariant. Les credentials et secrets ne figurent jamais dans ces métadonnées. Les états volumineux demandent un encodage borné ou une extension contractuelle explicite, sans déplacer silencieusement le curseur vers un cache.

La lecture d’un run resolve une fois un ensemble d’éditions. Elle ne remplace pas un pin manquant par la dernière donnée disponible. L’édition lie aussi la version sémantique, les field IDs et les paramètres de transformation. Une VIEW versionne sa définition et les bindings ; une lecture reproductible reçoit un ensemble d’entrées précis. Publier plusieurs sorties requiert un manifeste de release lui-même porté par une édition Iceberg publiée, qui référence leurs snapshots validés. Des commits successifs de références individuelles n’offrent pas, seuls, une publication atomique du groupe.

Le schéma Iceberg est une propriété de la table : les branches ne créent pas des univers de schéma indépendants. L’expansion compatible et la contraction suivent les règles de migration du document 04. Un changement incompatible nécessite un plan, une validation des lecteurs, voire une table de remplacement. Un fast-forward de données ne remplace pas cette procédure.

Après une réponse de commit perdue, le coordinateur recherche son identifiant de publication avant de réessayer. Un lease Flows réduit le travail concurrent, mais le catalogue doit encore refuser une tête inattendue. Le fencing doit agir au point de commit ou être garanti par une sérialisation prouvée du publisher, failover compris. Lire un TTL puis committer ailleurs laisse une course. Une annulation clôture le droit de publier avant de nettoyer le calcul ; après publication, elle rapporte le résultat réel et permet l’acquittement restant. Après une publication réussie, une panne de Postgres ou d’acquittement ne rend pas l’édition inexistante. La reprise lit le snapshot publié et acquitte la plage couverte sans la republier. Un journal durable de contrôle conserve les commandes, annulations, runs échoués et effets externes qui ne sont pas reconstruisibles depuis les seules éditions réussies. Ce journal ne remplace jamais la vérité d’ingestion.

6. Icegres, moteur Rust à intégrer sous le contrat d’édition

L’arbre local Icegres, base e0c175f avec modifications utilisateur conservées, contient des composants utiles : DataFusion, scans Iceberg, Arrow Flight, pgwire, contrôle d’ascendance et commit avec préconditions sur les références. La réutilisation porte sur ces composants. Le binaire actuel ne constitue pas encore le service de publication Hemera.

Une écriture synchrone directe sur main reste incompatible avec WAP. Le pilote commence par des lectures autorisées et épinglées, puis ajoute les écritures de staging et receipts, avant de qualifier les mutations et la maintenance. Les chemins de lecture de deletes positionnels et d’égalité existent dans la dépendance épinglée ; les deletion vectors Puffin ne sont pas pris en charge dans ce chemin. Aucun succès de lecture universelle v3 n’est déduit de cette revue statique.

Références de code à consulter dans l’arbre étudié : icegres/src/flight.rs pour identité, receipt et découverte ; branch.rs et overwrite.rs pour les commits ; cache.rs pour pins et providers ; buffer.rs, compact.rs et maintain.rs pour les mécanismes à encadrer.

7. Eidos, sémantique et actions sur les éditions

Eidos, base c162af2 avec refactorings locaux conservés, sépare déjà compilateur, core et serveur Rust. Sa vue autorisée via OpenFGA et ses contrôles lors des actions sont réutilisables. L’activation du registre et les écritures doivent rejoindre les contrats Hemera.

  • Le principal HTTP actuel vient de x-eidos-user et crée une identité de développement aux claims vides. Les routes registry et certains exports ne reprennent pas les contrôles de la vue autorisée. Il faut fermer ces accès et propager sujet, acteur et tenant vérifiés.
  • Un update du registre peut conserver l’état actif tout en remplaçant la définition. Le draft doit être séparé du modèle publié. Le modèle actif devient un bundle immuable dans un dataset sémantique Iceberg, avec hash et bindings stables.
  • snapshot() choisit le plus récent committed_at. Il peut donc prendre un snapshot staging. Les counts et backfills vecteurs ont aussi des lectures non pinnées. Le résolveur commun doit fournir l’édition avant toute lecture.
  • Apply exécute plusieurs DML séparés ; undo compare avant d’écrire dans un autre appel. Ces chemins ne sont pas un commit atomique sous préconditions. Une action produit un plan immuable, appliqué par Flows sous WAP ; undo produit une compensation soumise aux mêmes règles.
  • Le registre, les counts et les index vecteurs deviennent des projections par édition. Les drafts et le journal des effets restent sauvegardés. Reconstruire une projection ne doit pas relancer des notifications ou des webhooks.

Un plan Eidos porte l’édition sémantique, les snapshots d’entrée, les UUID/field IDs, les révisions attendues, l’identité, l’approbation éventuelle et la clé d’idempotence. La validation métier précède la publication. L’approbation se rapporte à ce plan précis ; modifier les entrées ou le plan la rend caduque. Les SDK, MCP et exports Ossie/JSON-LD rendent uniquement une édition autorisée et identifiable.

Références de code : crates/eidos-server/src/api/registry.rs, api/exports.rs, engine/apply.rs, engine/undo.rs, readmodel/refresh.rs et semantic.rs ; crates/eidos-core/src/flight/exec.rs, pg.rs et registry.rs. Le premier gate est une lecture Eidos → Icegres prouvée sur une édition exacte, avec révocation et découverte interdites testées.

8. Identité sans JVM et accès aux octets

IAM garde les identités métier et les politiques Cleyrop. L’IdP réalise l’authentification standard ; OpenFGA évalue les relations ; Lakekeeper gouverne les objets physiques. Un même serveur OpenFGA ne rend pas leurs modèles interchangeables. Les permissions métier de consultation, publication, téléchargement, sensibilité et délégation se projettent uniquement lorsque le modèle physique sait les représenter.

ZITADEL auto-hébergé est un candidat sans JVM, à qualifier. La sélection exige une version et une licence adaptées, un fonctionnement sans accès Internet, la parité des fédérations, MFA/passkeys, délégations, durées et révocations. Les documentations token exchange et migration des utilisateurs établissent des mécanismes disponibles, pas une migration Cleyrop déjà validée.

La migration garde un identifiant métier stable et une correspondance explicite issuer + sub. Elle ne fusionne pas les comptes par courriel. Les sessions et refresh tokens ne sont pas présumés portables. Une période bornée accepte les deux émetteurs, puis force la réauthentification et révoque l’ancien. Les secrets applicatifs sont renouvelés ; les authentifiants non transférables sont réenrôlés.

WAP n’est pas une barrière de confidentialité suffisante. Le banc local Lakekeeper 0.12.0/OpenFGA a reproduit une lecture de données staging avant publication puis après suppression de la branche, avec un grant select de table et remote signing, sans clé S3 client. Main est resté intact. La preuve figure au document 10. Une branche rejetée peut laisser snapshots, manifests et fichiers accessibles dans le périmètre de la table. Les lecteurs gouvernés passent par des moteurs ou services qui autorisent l’ensemble des objets d’une édition publiée. Copier des fichiers dans un préfixe lisible avant le commit expose aussi les candidats dont le commit perd la concurrence.

La cible de base maintient le stockage de travail privé. Icegres applique les politiques à chaque scan et aux métadonnées, jointures et requêtes préparées. Files contrôle les blobs par édition et par droit. Une capability courte lie sujet, acteur, tenant, audience, opération, édition et politique. Les règles de lignes/colonnes nécessitent une exécution médiée ou une matérialisation filtrée. L’accès Iceberg natif attend une preuve équivalente sur les objets, pas seulement un grant sur la table.

Un objectif initial de révocation en 60 secondes est à mesurer sur les chemins médiés, y compris flux déjà ouverts. Un credential distribué et encore valide a sa propre durée résiduelle. Les pannes de politique ferment l’accès sensible. La documentation storage Lakekeeper 0.12 et les modes de cohérence OpenFGA définissent les mécanismes disponibles ; la portée par édition relève du contrat Hemera à implémenter et tester.

Le décompte reprend le document 02. SOURCE, OP et TEST sont des nœuds de flow, pas des kinds supplémentaires. Les adaptateurs masquent les moteurs tout en exposant leurs limites. Un outil non compatible avec le contrat refuse le plan avant son exécution.

Un manifeste source() commun au code et à l’interface porte identifiant stable, connecteur/version, référence de secret, streams, mode, contrat, audits, bornes, cadence, journal, dédup, watermark et protocole d’acquittement. Sa représentation canonique est versionnée. Les positions contiennent source, époque, partition et offset exact ; les entiers longs ne traversent pas JavaScript comme nombres flottants. Les URI excluent credentials et paramètres sensibles. Un curseur opaque nécessaire à la reprise se chiffre avec une clé hors catalogue au lieu d’être simplement haché.

La définition logique, les éditions d’entrée et la clé d’opération sont des empreintes distinctes. La clé d’opération reste stable entre tentatives, tandis que tentative et fencing changent. Les audits, le contrat, le compilateur et le moteur font partie des entrées pertinentes de validation. Le fingerprint du prototype ne suffit pas encore à exprimer ces règles.

10. Remplacer Spark et Trino sans promettre une parité absente

DataFusion est une bibliothèque de calcul. Icegres lui apporte des protocoles, le catalogue et des opérations Iceberg, mais ne devient pas un moteur distribué par cette seule intégration. La cible distingue les requêtes interactives sur un nœud, les jobs bornés Python/DuckDB et le calcul distribué. Le placement change l’exécutant, pas le contrat des entrées et des éditions.

Sources officielles consultées le 2 octobre : DataFusion, architecture Ballista, bindings Python Ballista, matrice Iceberg Sail, migration Spark/Sail, écriture DuckDB/Iceberg. Les pages courantes sont une source de candidature ; la qualification exige ensuite tag, dépendances et digest d’image.

Flows reste propriétaire du run. Le scheduler d’un moteur distribué répartit seulement les tâches de ce run. Le plan transporte UUID, snapshots, schémas, specs, versions de codecs, dialecte, UDF et budgets. Les fichiers de shuffle ne sont pas la vérité d’ingestion. Le worker ne peut déplacer main, modifier le schéma global ni acquitter la source. Les UDF Python s’exécutent hors du serveur de contrôle, dans une image et un environnement isolés.

La sortie des JVM exige un inventaire des workloads réels : SQL BI, gros joins, skew, UDF Scala/Java, RDD, connecteurs JDBC, streaming et notebooks. Chaque workload reçoit un statut porté, à réécrire ou bloqué. La parité vérifie valeurs et types, nulls/NaN, décimaux, fuseaux, field IDs, partitions évoluées, deletes, limites et erreurs. Le banc a déjà trouvé une différence sur substr('abc',0,2) entre Spark et DuckDB. La compilation ou la compatibilité de protocole ne suffit donc pas.

Viennent ensuite les pertes de scheduler/exécuteur, refresh des credentials, révocation, spill, quotas, restauration et mises à niveau. Les seuils de latence/débit viennent des engagements et données clients à inventorier. Pendant la migration, un retour temporaire au moteur JVM de référence reste possible sur les mêmes éditions. Après retrait, le repli est un moteur sans JVM qualifié, une décomposition dont l’équivalence est démontrée, ou le refus explicite du workload. Un workload nécessaire encore dépendant d’une JVM bloque la cible finale.

11. Journaux, flux industriels et fichiers

Le broker sort de la JVM. Pour les nouveaux flux internes, NATS JetStream est un candidat Go sous Apache-2.0. Redpanda reste une option C++ lorsque la compatibilité Kafka est nécessaire. Sa licence et ses fonctions doivent être examinées pour le mode de distribution Cleyrop ; un binaire sans JVM ne prouve pas non plus une chaîne de reconstruction sans JVM, notamment avec Bazel en amont. Sources : NATS v2.15.0 inspecté, compatibilité Redpanda et licences documentées. Aucun broker n’a été qualifié en charge par cette mission.

Un journal relisible relève de la classe A. MQTT, webhooks et subscriptions sans historique relèvent de B avant capture. Une file supprimant à l’ack relève de C. Le produit seul ne détermine pas la classe : LimitsPolicy JetStream conserve selon des limites, alors que WorkQueue/Interest peuvent supprimer après acquittement. Le curseur publié utilise identité et génération du stream, partition et séquence du journal. La position d’un consumer ou sa fenêtre de déduplication ne remplace pas ce curseur.

Le réceptacle HTTP répond après prise en charge durable, avec une identité consultable. Il ne promet pas que l’édition est publiée. La consommation destructrice attend le receipt de publication. Le contrat JetStream documente un fsync périodique par défaut ; un PubAck n’établit donc pas seul la résistance à la panne système attendue. La qualification doit fixer synchronisation disque, réplication et domaines de panne, puis mesurer perte et débit. La rétention couvre indisponibilité, replay et reconstruction ; son épuisement bloque et alerte.

Les connexions de capture MQTT/OPC UA peuvent rester ouvertes dans une passerelle mutualisée. Elles n’imposent pas un daemon de traitement par source. Les runs gouvernés sont bornés. Sparkplug seq reboucle à 255 ; l’identité doit aussi distinguer l’émetteur et son époque. NDEATH appartient à Sparkplug. Une coupure OPC UA ne se rattrape que si HistoryRead et une rétention suffisante sont effectivement disponibles. Les corrections d’historian et données tardives créent des éditions de rattrapage auditées. Sources : Sparkplug 3.0 et OPC UA HistoryRead.

Files doit migrer son autorité, pas seulement son langage

Dans le code actuel, Files conserve sa hiérarchie dans PostgreSQL, génère des clés objet UUID+nom et indexe un SHA-256. Il ne réalise pas encore le stockage adressé par hash et le refcount décrits dans l’ancien design. Le téléchargement est médié par streaming, sans presign trouvé dans les chemins examinés. L’upload par morceaux utilise un temporaire local et flock ; la reprise par un autre worker reste à établir. Les gardes antivirus divergent entre téléchargement et preview dans le code lu, sans test d’exposition d’un déploiement.

La cible prépare un index FILESET Iceberg sur un stage unique, avec version physique immuable, hash, provenance et scans. Le snapshot reçoit ses propriétés avant le commit de publication. Les octets restent privés jusque-là. L’archive ou suppression du fichier source intervient après le receipt. SFTP ne peut reprendre sur le seul nom ou mtime : il faut une version stable, ou une copie privée dont l’intégrité est vérifiée. La terminaison OpenSSH existante reste possible derrière le contrôle Rust.

Le GC marque les objets atteignables depuis éditions conservées, tags, environnements, runs actifs et besoins de restauration. Les refcounts sont des caches. Avant suppression il relit les racines après un délai de sécurité. Une projection Catalog en retard ne suffit jamais à déclarer un blob orphelin. Les objets adoptés chez un tiers gardent un propriétaire et une dépendance de conservation explicites.

L’effacement suit également les textes extraits, chunks, vecteurs, snapshots et sauvegardes. Les états « retiré du service », « purgé du stockage actif » et « traité dans les sauvegardes » restent distincts. La restauration ne doit pas réexposer un objet interdit. La migration conserve IDs, dossiers, endpoints et permissions, puis bascule un corpus à la fois vers le publisher unique. Elle réutilise les intentions durables de suppression et l’outbox actuelles avec un transport sans JVM.

12. IA, modèles et vecteurs gouvernés

Le proxy IA actuel possède déjà deux applications et listeners, contrôle et données. Le port Rust conserve cette séparation, les contrôles IAM, les secrets chiffrés et l’annulation. Les workers Python/C++ pour entraînement et inférence restent possibles sans JVM. Un pool d’inférence disponible entre les requêtes ne contredit pas les runs bornés d’ingestion et de transformation.

Le stockage de chunks actuel peut exposer simultanément ancienne et nouvelle génération pendant le remplacement dans Milvus. Le serving cible construit une collection privée depuis une édition EMBEDDINGS unique, puis expose une collection prête et autorisée. Chaque réponse annonce l’édition réellement servie et son éventuel retard. Dimension, normalisation, métrique, tokenizer, modèle et découpage appartiennent au contrat. Une réindexation ne change pas silencieusement la source des pages suivantes.

Les hits Eidos sont filtrés, mais les compteurs dropped_unauthorized et examined publics du chemin observé peuvent renseigner sur des candidats interdits. Ils passent dans la télémétrie opérateur. Les droits sont vérifiés avant restitution du texte et avant son envoi au LLM ; les caches sont bornés par édition et politique. Les applications n’utilisent pas un credential vectoriel partagé permettant de contourner ce contrôle.

MODEL publie un manifeste Iceberg avec poids immuables, hashes, format, runtime, hyperparamètres, entraînement/évaluation épinglés et métriques d’audit. Importer un modèle externe n’invente pas un lignage d’entraînement inconnu. Une signature indique une provenance, pas l’innocuité d’une désérialisation. Les formats exécutables restent confinés avec limites CPU/GPU/mémoire/réseau. FEATURESET distingue temps événement et temps de disponibilité pour empêcher la fuite d’information future dans l’entraînement.

Le template Milvus observé désactive Pulsar et utilise RocksMQ en mode non distribué. Il ne justifie donc pas à lui seul un retrait pour présence de JVM. Tout passage au distribué exige une nouvelle inspection des dépendances. L’index demeure une projection quel que soit le moteur. Les tests couvrent perte totale de l’index, dimension changée, révocation pendant recherche, panne GPU, publication avant indexation et deux promotions concurrentes.

Une purge atteint chunks, caches, citations et collections dérivées. Un modèle déjà entraîné exige sa propre décision de retrait ou réentraînement ; supprimer des vecteurs ne démontre pas l’effacement de son apprentissage. Un rollback reste soumis aux droits et interdictions actuels.

13. SDK et outils tiers derrière le même contrat

Le SDK Cleyrop actuel offre des transports HTTP synchrones/asynchrones et de l’authentification réutilisables. Le SDK lake à éditions est un nouveau contrat. Python, TypeScript, CLI, API et no-code produisent le même IR versionné et les mêmes erreurs. Les bindings ne possèdent pas une copie autonome du publisher.

La compilation elle-même doit être isolée. Le prototype exécute les modules Python en découvrant les modèles, y compris pour ls ou plan. Macros et plugins tiers ont aussi des effets possibles. Ils s’exécutent sans secret de publication, avec entrées et réseau contrôlés. Le core Rust valide l’IR, fixe les éditions et choisit un moteur capable d’exécuter le plan.

dbt et SQLMesh restent dans une région privée. Les tests bloquent la sortie gouvernée. CTAS, CREATE OR REPLACE, DROP, RENAME, GRANT, hooks et évolution du schéma global ont chacun une règle explicite ; une option de branche ne les rend pas tous privés. Les états SQLMesh/dlt ne déterminent jamais la reprise source. Le wrapper dlt reconstruit son état depuis l’édition publiée et rend un état candidat. Un succès de load n’autorise pas un ack.

Sources primaires : hooks et opérations dbt, instructions de modèles SQLMesh, état dlt et destination Iceberg dltHub. Cette dernière relève d’une offre commerciale documentée ; son support Lakekeeper ne prouve pas le contrat WAP ni sa disponibilité dans tous les chemins dlt.

Commencer par SQL natif et sorties Arrow privées, puis qualifier les régions dbt/SQLMesh sur moteurs sans JVM. La présence de pgwire ou Flight SQL ne prouve pas qu’un adaptateur dbt Postgres fonctionne sur Icegres. L’ancien SDK PySpark reste une compatibilité de migration à portée déclarée. Les artefacts tiers sont filtrés avant import dans Catalog, car SQL compilé, chemins et paramètres peuvent contenir des données sensibles.

14. Conserver les parcours, corriger les états exposés

Les 30 écrans du document 03 restent une base utile. Le frontend React/TypeScript conserve son design system, ses clients et ses contrôles d’accès. Un adaptateur OIDC remplace le couplage keycloak-js. Les fonctions de consultation Iceberg et de navigation sémantique du laboratoire enrichissent Catalog, sans afficher tous les snapshots physiques à tout lecteur.

La fiche, la pagination, les statistiques et l’export utilisent une même édition. Les clés de cache incluent sujet, projet, environnement, édition et version sémantique. Changer de contexte annule les requêtes précédentes. Les événements SSE ont un identifiant de reprise ; une reconnexion recharge l’état si le journal ne couvre plus le curseur. Un événement retardé ne fait pas régresser la projection.

S14 distingue la version d’un flow de l’édition des données. S16 distingue préparation, audit, conflit, publication et ACK_PENDING. Après perte de réponse, le client recherche le receipt idempotent au lieu de relancer l’ingestion. S8 expose curseur publié, plage préparée et ack observé séparément. Il n’offre pas de modification directe du curseur dans Flows PG. Une dérive de schéma ouvre un nouveau plan.

Deux promesses du design initial sont remplacées. S19 retire « Publier en forçant » après veto : une dérogation demande une nouvelle politique approuvée et de nouveaux audits. S20 ne promet pas une vue multi-table cohérente grâce à des promotions séquentielles ; il affiche une release explicitement épinglée ou un état partiel. Un rollback n’annule pas un ack déjà émis.

Les routes de liste/détail d’actions Eidos doivent être autorisées avant exposition des plans et paramètres. Le droit de découverte gouverne noms, colonnes, volumes, relations et complétions. Un cadenas ne révèle un objet que si sa découverte est autorisée. Le serveur contrôle ces droits indépendamment des boutons visibles.

Des façades compatibles conservent temporairement /datasources, /dataflows, /executions et /datasets, puis traduisent vers Sources/Flows/Runs/Catalog. Les tests de parcours couvrent veto, conflit après approbation, réponse perdue, ack tardif, révocation pendant pagination, SSE et confusion dev/prod, avec accessibilité clavier et langues existantes. Aucun test UI n’a été exécuté dans cette étude.

15. Exploitation, livraison et reconstruction

La chaîne Cleyrop possède déjà des candidats de release par composant, SBOM, signatures et preuves e2e, avec promotion du digest testé. Ces mécanismes accueillent les unités Rust. Les nouveaux chemins sont déclarés dans le planner CI du monorepo ; les versions restent pilotées par le moteur de release. Les contrats REST/Protobuf survivent dans les adaptateurs jusqu’à migration de leurs consommateurs.

Le retrait JVM et la migration des cœurs métier sont deux critères distincts. IAM, Files et app-management sont déjà sans JVM mais restent en Python. La cible transfère leurs règles dans Rust, puis retire les façades transitoires. Rust, Cargo.lock, features et dépendances natives sont épinglés. Les versions Arrow différentes d’Icegres et Eidos exigent des tests de protocole, pas une mise à niveau globale supposée suffisante.

L’airgap qualifie une installation réelle sans réseau sortant, avec images, dépendances, certificats, ressources de l’IdP, modèles et outils de maintenance disponibles localement. Le rendu Helm ne la prouve pas. cargo vendor et cargo build --frozen participent au build hors ligne ; les scripts natifs et outils de génération doivent aussi être audités. Sources : Cargo vendor et Cargo build. L’émulation ARM de CI ne remplace pas la validation sur les architectures natives promises.

La politique Expand/Migrate/Contract reste applicable aux schémas SQL Rust. Expand et Contract partent dans des versions distinctes avec preuve du retour au binaire précédent. L’enforcement actuel couvre seulement certains arbres Alembic ; il faut étendre les contrôles avant d’introduire de nouvelles migrations. Le changement de langage ne dispense pas de sauvegarder identités, policies, drafts et données de contrôle durables.

Les valeurs CNPG étudiées laissent l’archivage WAL optionnel désactivé par défaut et désactivent les backups en profil micro. Elles ne prouvent donc pas un RPO de production. La restauration doit couvrir catalogue, objets, politiques, clés nécessaires au déchiffrement, journal durable et effets externes. Les éditions reconstruisent les projections de données, pas les mots de passe, plans non publiés et événements jamais publiés.

Les logs corrèlent dataset, édition, run, tentative, fence et audit sans jeton ni contenu métier. Les métriques prioritaires sont lag source, couverture de rétention, refus d’accès, veto, conflit de publication, ack en attente, reprises et objets orphelins. Une absence d’événement déclenche une réconciliation ; elle ne signifie pas absence de commit.

Les contrôles finaux inspectent images applicatives, init containers, opérateurs, notebooks, hooks, jobs de migration, JARs Hadoop/JDBC, builders et générateurs. Un composant tiers activant indirectement Pulsar, Kafka ou une autre JVM échoue au critère final. Les licences de redistribution et exceptions de dépendances doivent être établies pour les composants retenus. Cette étude ne copie aucun code privé d’Icegres ou Eidos dans le dépôt public.

Huit campagnes de restauration à exécuter

Le time travel lit une édition historique sans déplacer le checkpoint actif. Restaurer une ingestion derrière des acks impose de suspendre les writes, comparer les frontières et rejouer l’intervalle manquant. Si la rétention ne le couvre plus, la reprise automatique est bloquée et un resnapshot contrôlé ouvre une nouvelle époque. Recopier un curseur avancé sur des données anciennes qui ne couvrent pas sa plage est interdit.
