Service actuel · process-data

Exécution des flows, planification et ressources de calcul

22 capacités analysées

services/process-data · Kotlin 2.4.10, Spring Boot 4.1.1 et JVM 21 observés dans Gradle. PostgreSQL/JPA/Flyway, Kafka/Protobuf avec outbox/inbox, Quartz JDBC clusterisé pour cron, boucles Spring de réconciliation, S3, REST app-management et HTTP vers les processus de session Python/PySpark.

Service qui reçoit les versions exécutables produites par data-dev, crée et suit les runs et jobs, orchestre les sessions Python/PySpark, gère les déclenchements, clusters et images, expose historique et temps réel, et relaie les états aux autres services.

Lecture de codePas de qualification runtime nouvelle

Domaines cible : Runtimes, Flows, IAM, Writer, Publisher, Query, Applications, Notifications, Audit, Migration, Maintenance, Egress.

Périmètre de lecture

  • Controllers execution, schedule, session, image et admin, DTO de soumission et filtres.
  • Agrégats DataflowVersion, Script, ExecutionStorageManifest, DataflowExecution, jobs, files persistantes, Cluster, Session et schedules.
  • Handlers de run manuel/automatique/partiel, soumission, suivi, logs, fin de job, annulation et callback Spark.
  • Adaptateur app-management et appels directs de sessions, cycle de clusters/images, bibliothèque PyPI, startup et réconciliation.
  • Consumers DataDev/ProcessData/IAM, outbox/inbox/DLT, maintenance PostgreSQL, RunnerAuthorizationClient, manifestes Gradle et chart.

Objets et cycle de vie

  • DataflowVersion : copie exécutable reçue de data-dev, avec scripts, dépendances, manifestes, propriétaire, branche et projet réel d’exécution ; ce n’est pas une édition de données publiée.
  • DataflowExecution : run avec statut, déclencheur, principal, cluster, échéance de capacité, dates et jobs. L’exécution partielle conserve des résultats antérieurs marqués comme réutilisés.
  • DataflowJobExecution et JobDetails : script, étapes, sorties, logs et flag historique isSparkCommitted. Les statuts finaux ne décrivent pas à eux seuls un reçu de publication.
  • DataflowSubmission, JobSubmission, JobSubmitted, JobCompleted et ExecutionCancelled : intentions et étapes de progression durables utilisées pour reprendre après incident.
  • Cluster et Session : capacité persistante Python/PySpark, ressources, images, état observé, pause et suppression différée.
  • Image, ImageUpdate et Library : base, environnement personnalisé, demandes de packages, builds et historique.
  • DataflowSchedule : expression/fuseau ou déclenchement événementiel ; Quartz stocke jobs, triggers et heartbeat.
  • Miroirs User/Project/ProjectMember, correspondances IAM, outbox, inbox, quarantaine, chunks de logs et suivi de migration.

Dépendances du service

  • Data-dev produit VersionEvent, changements de propriétaire, suppressions et triggers ; process-data renvoie états de run, schedules et clusters.
  • App-management reçoit les appels REST de session, serveur Spark Connect, submission, cancellation, inventaire et build d’image ; les sessions exposent aussi leur état/job en HTTP.
  • S3 héberge les archives de scripts ; le run obtient une URL signée vers la version/script. Le contenu effectif et les versions déployées ne sont pas inspectés.
  • IAM autorise les opérations de runner et fournit les miroirs ; gateway protège les routes externes ; Notification Center relaie les mises à jour de clusters.
  • PostgreSQL conserve contrôle et historique ; Kafka transporte Protobuf et événements ; Quartz ajoute la planification clusterisée ; PyPI/index interne fournit les bibliothèques.

PD-01Cible non qualifiée

Réception des versions et intégrité du manifeste

Comportement observé

Le consommateur VersionEvent réclame une clé d’inbox dans sa transaction puis construit une version locale. VERSION_SAVE conserve la version sans run. MERGE, PUBLISH, COLLECT, PREVIEW, DELETE, EMPTY_DATASET et UPDATE_COLUMN peuvent lancer automatiquement le traitement si le démarrage des clusters est actif. Les actions inconnues sont rejetées pour retry/DLT. Une version dupliquée ne ressuscite pas une version supprimée. Le handler peut enrichir uniquement un manifeste absent ; il vérifie le même ensemble de scripts et refuse un manifeste non nul divergent. Il préserve les autres métadonnées de la version existante. La portée execution_project_id vient du producteur et une valeur invalide ne devient pas un runner global.

Utilisateurs et rôles

Data-dev, service de migration et exécuteur.

Interfaces dans le code

Données et états

Dépendances et échanges

Data-dev par Protobuf/Kafka, PostgreSQL et contrôleur de runs.

Comportement cible proposé

Flows/Runtimes Rust acceptent un RunSpec immuable et versionné. Un même ID ne peut désigner des artefacts ou droits différents. Les versions anciennes sans manifeste sont isolées jusqu’à preuve ou conversion explicite.

Migration de cette capacité

Importer versions, scripts, manifestes et inbox de manière cohérente. Conserver les références d’origine mais remplacer les IDs synthétiques d’opérations techniques par un type de run explicite. Ne jamais reconstruire des droits depuis le flow courant.

Critère d’acceptation à exécuter

Rejouer la même version avec un manifeste égal, absent puis divergent. Les deux premiers cas conservent les droits existants ; le troisième est refusé. Rejouer une version supprimée ne la remet ni en file ni en service.

PD-02Cible non qualifiée

Lancement manuel d’un flow complet

Comportement observé

Le lancement manuel attend que la version demandée soit visible, refuse une version supprimée et une version sans script, puis consulte la dernière exécution de sa branche. Si elle est CREATED, PENDING ou RUNNING, il refuse un nouveau run concurrent selon la règle métier locale. Le cluster vient de l’override de requête, de la version ou du précédent run, avec repli vers un cluster par défaut du type attendu. Le service crée un DataflowExecution, calcule son nom numérique par comptage des exécutions du projet, persiste ses jobs éventuels puis émet ExecutionCreatedEvent. Le demandeur authentifié devient le principal MANUAL_CALLER distinct du propriétaire de version.

Utilisateurs et rôles

Utilisateur autorisé à exécuter le flow.

Interfaces dans le code

POST /dataflows/{id}/versions/{version}/run, paramètre cluster optionnel ; DataflowVersionRunManualCommand.

Données et états

Dépendances et échanges

Versions répliquées de data-dev, clusters, miroirs utilisateurs/projets, outbox d’exécution et notifications.

Comportement cible proposé

Runtimes Rust accepte une commande idempotente par projet et version, acquiert une réservation atomique de concurrence et fige RunSpec. Le run est borné en temps, octets et ressources, indépendamment du pod worker.

Migration de cette capacité

Conserver la politique de concurrence par branche ou la faire évoluer explicitement. Remplacer le contrôle lecture-puis-écriture par une contrainte/lease transactionnelle. Corréler le flow de l’URI avec la version persistée dans le nouveau contrat.

Critère d’acceptation à exécuter

Envoyer deux requêtes concurrentes de même clé de commande sur deux replicas. Elles retournent un seul run. Deux clés différentes visant une branche limitée à un run produisent un gagnant et un conflit déterministe.

PD-03Cible non qualifiée

Exécution partielle d’une transformation et réutilisation d’amont

Comportement observé

La route de transformation résout le script correspondant à l’identifiant métier de transformation. Elle refuse un dernier run de branche encore actif, choisit un cluster puis calcule les dépendances à relancer. Un amont dont le job précédent est SUCCESS ou WARNING n’est pas ajouté à la fermeture de dépendances. Le nouveau run peut copier des jobs du précédent avec de nouveaux IDs et isFromAnotherExecution=true, tout en relançant les scripts sélectionnés. Les dates de démarrage, la session et la deadline sont renouvelées. Le résultat est marqué isPartialRun ; le statut global ignore certains jobs copiés dans son calcul d’échec.

Utilisateurs et rôles

Développeur qui corrige ou inspecte une transformation.

Interfaces dans le code

Données et états

Dépendances et échanges

Historique des jobs de branche, graphe de dépendances de la version et runtime de session.

Comportement cible proposé

Runtimes Rust réutilise uniquement des résultats liés à des éditions d’entrée et artefacts immuables prouvés. La sélection d’un sous-graphe enregistre les dépendances réutilisées, leur provenance et la politique d’invalidation.

Migration de cette capacité

Ne pas convertir isFromAnotherExecution en preuve suffisante de réutilisation. Importer cette information comme provenance historique, puis exiger digests, éditions et paramètres pour les nouveaux runs partiels.

Critère d’acceptation à exécuter

PD-04Cible non qualifiée

Identité d’exécution, projet réel et durée d’autorisation

Comportement observé

L’exécution conserve ExecutionPrincipal avec MANUAL_CALLER, SCHEDULED_OWNER ou INTERNAL_OWNER. Les runs planifiés capturent le propriétaire de la version utilisée ; les manuels capturent le demandeur. La deadline d’autorisation est fixée à la création et le repository conserve celle de la ligne verrouillée lors des sauvegardes. Submit refuse de lancer un job après cette borne. Pour les jobs de flow/preview, le projet vient de la version ; pour collecte/suppression/vidage/colonnes, il vient de executionProjectId, distinct des anciennes références synthétiques. Le service n’envoie pas directement le manifeste dans SubmitJobRequestDTO ; app-management reçoit les IDs du job et doit résoudre les droits selon son propre contrat.

PD-05Cible non qualifiée

Files persistantes et progression du graphe de jobs

Comportement observé

ExecutionCreatedEvent fait passer une exécution CREATED à PENDING et crée DataflowSubmission. La file est ordonnée par cluster et expose une position. Le démarreur charge les clusters et jobs déjà soumis, cherche une session libre et crée des JobSubmission pour les racines du graphe. Une session est choisie parmi les IDLE sans job en attente/soumis ; les jobs d’un même flow peuvent rester rattachés à sa session. Les enfants sont déclenchés après succès et seulement si tous leurs amonts sont SUCCESS. Le traitement parcourt successivement nettoyage, sessions, annulation, démarrage, soumission, suivi et fin de job. Cette boucle est un @Scheduled du pod ; elle n’est pas le job Quartz utilisé pour les cron.

Utilisateurs et rôles

Interfaces dans le code

Dépendances et échanges

PostgreSQL, ClusterService et événements de succès/session.

Comportement cible proposé

Runtimes Rust possède un ordonnanceur durable avec claims atomiques, leases bornés, tentative monotone et déduplication. Les files ne donnent pas de droits au stockage. Le worker remplaçable ne modifie jamais le checkpoint publié.

Migration de cette capacité

Conserver les identifiants de commande/job lors de la transition. Remplacer les séquences d’appels au repository par des transactions définies. Qualifier la fenêtre entre création distante du job et enregistrement local avant montée en replicas.

PD-06Cible non qualifiée

Soumission aux sessions Python et Spark Connect

Comportement observé

Submit examine JobSubmission et évite un nouveau job si la session possède déjà un JobSubmitted. Il exige une session IDLE, charge l’exécution, refuse un run final ou hors deadline et soumet via ClusterService. L’adaptateur crée une URL S3 présignée pour l’artefact version/script puis envoie job, cluster, session et projet à app-management. Une création distante valide devient job RUNNING, JobSubmitted et session BUSY. Une session absente, invalide ou une réponse nulle déclenche FAILURE. Le statut et l’annulation du job passent ensuite directement par HTTP vers le processus de session. Les appels distants et écritures PostgreSQL ne forment pas une transaction atomique dans les handlers lus.

Utilisateurs et rôles

Ordonnanceur, app-management et processus de calcul.

Interfaces dans le code

POST app-management /private/sessions/jobs/submit ; HTTP de session submit/{statementId} ; ClusterConnectServerServiceAppManagementImpl.submitJob/getJobState/cancel.

Données et états

JobSubmission vers JobSubmitted avec StatementId distant ; session IDLE/BUSY ; artefact S3 référencé par URL courte.

Dépendances et échanges

App-management authentifié par client de service, S3, réseau de sessions Python/PySpark.

Comportement cible proposé

Runtimes Rust soumet un JobSpec à un adaptateur Kubernetes/processus non JVM. L’ID de tentative est idempotent côté exécuteur ; la réponse distante peut être retrouvée après perte réseau. L’artefact est vérifié par digest avant exécution.

Migration de cette capacité

Préserver les contrats de job et les reçus pendant le remplacement de l’adaptateur. Introduire une opération query-by-attempt pour résoudre une soumission ambiguë. Remplacer les sessions Spark Connect par workers bornés et pools Python adaptés.

Critère d’acceptation à exécuter

Faire créer un job distant puis couper la réponse. La reprise retrouve le même job par son ID de tentative, vérifie son digest et ne le crée pas une deuxième fois. Une URL d’artefact expirée donne une erreur reprise sans fallback de credentials.

PD-07Cible non qualifiée

États des jobs, étapes et sorties

Comportement observé

Le run et les jobs utilisent CREATED, PENDING, RUNNING, FAILURE, SUCCESS, SKIPPED, WARNING et CANCELED. Les états finaux d’un job ne sont pas remplacés par un nouvel état. Les détails associent transformation, étape, sortie, logs et un outputStatus distinct. Le suivi de session convertit available en succès, error en échec et un état inconnu en échec. Un job échoué marque les descendants non réussis SKIPPED. Une réussite déclenche les enfants admissibles. Le run devient terminal quand tous les scripts possèdent un job final ; WARNING peut contribuer à l’échec global, avec une règle propre aux runs partiels. Les messages Python renseignent aussi les étapes sans déterminer seuls le résultat global.

Utilisateurs et rôles

Exécuteur, bibliothèque Python, frontends et consommateurs de datasets.

Interfaces dans le code

ExecutionUpdateStatusCommandHandler ; JobCompletedCommandHandler ; ScriptExecutionEvent ; ExecuteFinalPipelineEvent.

Données et états

DataflowExecution, DataflowJobExecution, JobDetail et ExecutionState de sortie. Historiques terminal et de provenance des jobs repris.

Dépendances et échanges

Runtime de session pour résultat, Kafka pour messages de scripts et événements de fin, projection data-dev/data-model.

Comportement cible proposé

Runtimes Rust sépare état du calcul, état du candidat, décision d’audit et publication. Une sortie n’est disponible au lecteur que par une édition approuvée. Le vocabulaire legacy peut être exposé par une projection de compatibilité.

Migration de cette capacité

Écrire une table de transition et une matrice de conversion des états inconnus, WARNING, SKIPPED et reprises partielles. Éviter de recopier SUCCESS dans un statut de publication. Corréler les événements au run/tentative, pas seulement à version/script.

Critère d’acceptation à exécuter

Livrer successivement RUNNING, SUCCESS puis un RUNNING retardé pour une même tentative. Le job reste terminal. Un run avec un enfant sauté et un candidat refusé expose séparément ces faits et ne publie aucune sortie partielle non approuvée.

PD-08Cible non qualifiée

Comportement observé

Utilisateurs et rôles

Comportement observé

Le relay réclame les lignes non envoyées avec SKIP LOCKED, attend l’acquittement Kafka puis marque sentAt ; un échec conserve la ligne, incrémente attempts et stocke l’erreur. Architecture et exploitation du service cible

Plan de contrôle Rust proposé

  • API Rust de commandes de run, admission, tentative, annulation, planification et progression, avec idempotence, révision attendue et journal durable.
  • Flows fournit une révision immuable et un manifeste typé. Runtimes épingle entrées approuvées, environnement, paramètres, portée IAM, budget et échéance avant admission.
  • PostgreSQL reste l’autorité des commandes, identités et reçus d’effets ; les checkpoints publiés se lisent dans les éditions Iceberg approuvées.
  • Publisher coordonne les sorties et crée une release multi-sorties elle-même édition Iceberg, comprenant source/epoch/range/participants ; les lecteurs épinglent cette release.
  • Le statut du run distingue calcul, staging, audit, publication et effets. EXPORT est un effet ; EXPOSURE est un consommateur déclaré.

Plan de données proposé

  • Workers fongibles pour runs bornés, moteurs Rust/Arrow/SQL et Python isolé. Suppression finale des sessions Spark, Spark Connect, Quartz JVM, Kafka JVM et de toute autre dépendance Java.
  • Le worker soumet les octets au Writer de confiance. Il ne détient pas table.modify générique ; Publisher contrôle la publication après audit de fichiers immuables.
  • Tous les kinds TABLE, INCREMENTAL, VIEW, FILESET, MODEL, EMBEDDINGS, FEATURESET et STREAM utilisent WAP. Un flux éphémère est journalisé durablement avant gouvernance et traité par intervalles bornés.
  • Le candidat porte origin.* ; la preuve post-candidat est liée durablement sans réécriture du summary par fast-forward. UUID/refs/schema/spec/ascendance ne remplacent pas un protocole de fencing Hemera.
  • Publish-then-ack lie checkpoint publié et édition approuvée. Compaction suit le même circuit WAP ; expiration/GC utilisent un plan audité et les gardes de rétention.

Découpage du core Rust

  • runtimes-api : DTO compatibles, admission, autorisations et résolution des identités canoniques.
  • run-controller : machine d’états, files persistées, baux de tentative, réconciliation, annulation et receipts.
  • scheduler : occurrences durables, cron/fuseaux, événements, déduplication et politique de rattrapage.
  • environment-registry : locks Python, digests de conteneur, provenance et builders encapsulés.
  • worker-gateway : lancement, état, logs structurés et capacités bornées ; aucune API de publication générique vers le worker.
  • audit-projection : historique des runs/tentatives, lien aux publications approuvées, métriques et flux de notification reprenables.

Identité, autorisation et isolation

  • Conserver la distinction initiateur manuel, owner interne/planifié et projet réel des opérations fabriquées. Ne pas dériver des droits du seul owner courant ou du dataflowId synthétique.
  • Les dates de capacité persistées doivent survivre à la reprise. Une nouvelle tentative ne prolonge pas implicitement l’autorisation du run.
  • Le code utilisateur, packages, logs, URL signées et fichiers sont des surfaces tenant ; limiter octets, durée, réseau, secrets et scopes, avec redaction dans les diagnostics.
  • La suppression de projet/utilisateur conserve l’attribution historique sans conserver un droit d’accès. Les projections et caches ne sont pas une source d’autorisation autonome.

Exploitation et reprise

  • La lecture établit les mécanismes présents, pas leur qualification en multi-réplicas. Quartz clusterisé ne suffit pas à prouver la sûreté de la boucle Orchestrator de chaque pod.
  • Surveiller âge des files, durée d’admission, tentatives perdues, dead letters, relay attempts, silences runtime, dérive d’image, retard de schedule et différences entre fin technique et publication.
  • Sauvegarder PostgreSQL, artefacts et catalogue avec une procédure de restauration qui réconcilie les éditions déjà publiées ; ne pas traiter la base de contrôle comme checkpoint data autoritaire.
  • Qualifier redémarrage complet, rolling update, perte réseau après submit, arrêt pendant commit et callback retardé. Aucun de ces parcours n’a été exécuté dans cet audit.

Séquence de migration

  • Geler le contrat API/événements et un corpus représentatif : Python, SQL, PySpark, partial, preview, collect, delete, empty et update-column.
  • Importer IDs canoniques, versions, manifestes, profils, schedules et historique ; isoler les versions anciennes sans manifeste complet.
  • Construire scheduler et controller Rust en observation passive puis comparer leurs décisions sans lancer de travail concurrent.
  • Qualifier l’exécution sans JVM par opérateur, package et type de flow ; rendre les incompatibilités explicites avant activation.
  • Déployer Writer/Publisher, audit immuable, checkpoints d’édition et receipts ; qualifier les scénarios de panne et de multi-sorties.
  • Basculer par projet/profil après drainage ou reprise explicite des runs legacy ; attribuer chaque occurrence et run à un seul controller.
  • Réconcilier queues/outbox/DLT puis retirer process-data JVM, Spark Connect, sessions Spark, Quartz et transport Kafka JVM. Conserver les lectures d’historique nécessaires.

Écarts et décisions encore ouverts

  • Le contrat exact de succès attendu par les triggers FINISHED doit être décidé ; le handler lu ne filtre pas le succès source.
  • Le parcours schedule temporel requiert une exécution antérieure de production : confirmer la création initiale attendue côté produit.

  • Le submit distant peut réussir avec réponse perdue. La clé d’idempotence réellement garantie par app-management doit être qualifiée.
  • La sûreté multi-réplicas de la boucle de files et les limites des verrous observés exigent des tests de panne ; aucune garantie globale exactly-once n’est déduite.
