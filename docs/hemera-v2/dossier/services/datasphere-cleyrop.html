DSPC-01Cible non qualifiée

Construire et conserver un label de sensibilité

Comportement observé

PUT /labels reçoit UUID dataset, policy, classification et category, retourne 202 et lance une BackgroundTask. Le handler appelle le binaire Datasphere pour générer un JSON, encode ce JSON en base64 puis upsert le label en base. Une erreur de tâche est journalisée ; le 202 ne constitue pas une preuve de génération terminée. Le binaire propriétaire n’a pas été inspecté.

Utilisateurs et rôles

Gestionnaires de labels et service data-model.

Interfaces dans le code

PUT /labels ; BuildLabelCommandHandler ; DataspheresLabelServiceImpl.build_label.

Données et états

Label avec paramètres, JSON, base64 et dates PostgreSQL.

Dépendances et échanges

Binaire Datasphere .NET Linux x86-64, configuration/SPIF et base.

Comportement cible proposé

IAM/Audit Rust contrôle la politique et un job durable génère un label versionné lié à une édition ; adaptateur propriétaire à remplacer ou qualifier explicitement.

Migration de cette capacité

Importer labels et politiques, comparer byte/hash et décisions ; remplacer BackgroundTask par travail reprenable avec statut.

Critère d’acceptation à exécuter

Un 202 fournit un job consultable ; redémarrer après acceptation ne perd pas la génération ; paramètres identiques conservent le résultat attendu.

DSPC-02Cible non qualifiée

Relire le label et demander les décisions de clearance

Comportement observé

GET /labels trouve le label par UUID. POST /access/check reçoit des ressources et leurs sujets, valide les UUID, charge tous les labels et refuse les labels absents. Il construit pour chacun un metadata_binding base64 puis appelle le PDP /decide/by-id. L’adaptateur vérifie que la réponse est une liste de même cardinalité et la traduit en décisions par sujet ; réseau, TLS et retries sont configurables.

Utilisateurs et rôles

IAM, services consommateurs et utilisateurs soumis aux clearances.

Interfaces dans le code

GET /labels?id=... ; POST /access/check.

Données et états

Labels stockés et décisions retournées, sans pouvoir de publication.

Dépendances et échanges

Clearance PDP HTTP/TLS et repository de labels.

Comportement cible proposé

IAM Rust compose droits ordinaires et classification ; décisions versionnées avec politique, label et sujet, refus si indisponible selon contrat.

Migration de cette capacité

Rejouer matrice politique/classification/sujets ; comparer réponses et erreurs avant changement de PDP ou binaire.

Critère d’acceptation à exécuter

UUID invalide et label absent ne donnent aucun ALLOW ; une réponse partielle du PDP est refusée, avec traçabilité de la version de politique.

DSPC-03Cible non qualifiée

Extraire une table et produire un export chiffré ZTDF

Comportement observé

POST /labels/encrypt charge le label et télécharge la table par son tech_name via Spark. Le service écrit un seul fichier Parquet local en coalesçant, puis refuse un fichier vide ou supérieur à 2 Gio et le nettoie. Le binaire marque le fichier puis le chiffre en .ztdf ; le fichier est téléversé sur S3 et le répertoire temporaire nettoyé. Le code lit la table par nom sans pin d’édition explicite dans ce chemin.

Utilisateurs et rôles

Utilisateurs autorisés à exporter et opérateurs de données classifiées.

Interfaces dans le code

POST /labels/encrypt ; SparkFileServiceImpl.download_file ; LabelService.encrypt.

Données et états

Parquet temporaire, label, artefact .ztdf et objet S3.

Dépendances et échanges

Spark/JVM, Iceberg accessible au catalogue Spark, S3 et binaire Datasphere.

Comportement cible proposé

Query/Files Rust extrait une édition approuvée épinglée ; EXPORT reste un effet à reçu avec hash, politique et destinataire. Remplacer Spark et ses outils JVM.

Migration de cette capacité

Qualifier lecteur Arrow/Parquet sans JVM et compatibilité ZTDF ; borner les flux avant matérialisation et conserver preuves de label/édition.

Critère d’acceptation à exécuter

Exporter une édition donnée malgré une publication concurrente ; rejouer retrouve le même reçu ; aucun artefact privé n’est exposé avant contrôle de sortie.

DSPC-04Cible non qualifiée

Ordonner les travaux de chiffrement et surveiller les dépendances

Comportement observé

EncryptQueue est une asyncio.Queue en mémoire avec un worker démarré dans le lifespan. Le worker traite les jobs, journalise les exceptions puis marque la tâche terminée. Les instructions indiquent que les singletons Spark et queue sont créés au démarrage ; une panne d’initialisation Spark est seulement loggée et laisse l’encryption indisponible. Alembic est exécuté au démarrage ou via le mode migrate. Le 202 ne donne pas de reçu de livraison durable dans les routes lues.

Utilisateurs et rôles

SRE et opérateurs d’export.

Interfaces dans le code

EncryptQueue.start/stop/enqueue/_worker ; lifespan et mode migrate.

Données et états

File de jobs locale au processus et fichiers temporaires.

Dépendances et échanges

PostgreSQL, Spark, binaire et S3.

Comportement cible proposé

Flows/Files Rust possède une queue durable, leases, limites de stockage et reçus d’effets ; health reflète chaque dépendance requise.

Migration de cette capacité

Drainer les travaux connus, passer à une file persistée et tester reprises/cleanup avant retrait du runtime Spark.

Critère d’acceptation à exécuter

Arrêt après extraction puis reprise n’abandonne pas de fichier sensible ; un Spark absent ou son remplaçant indisponible empêche une readiness d’export trompeuse.

Architecture et exploitation du service cible

Plan de contrôle Rust proposé

  • IAM/Audit Rust contrôle la politique et un job durable génère un label versionné lié à une édition ; adaptateur propriétaire à remplacer ou qualifier explicitement.
  • IAM Rust compose droits ordinaires et classification ; décisions versionnées avec politique, label et sujet, refus si indisponible selon contrat.
  • Query/Files Rust extrait une édition approuvée épinglée ; EXPORT reste un effet à reçu avec hash, politique et destinataire. Remplacer Spark et ses outils JVM.
  • Flows/Files Rust possède une queue durable, leases, limites de stockage et reçus d’effets ; health reflète chaque dépendance requise.

Plan de données proposé

  • Lecture d’une édition autorisée puis production d’un export chiffré borné, avec reçu PostgreSQL ; aucune écriture directe Iceberg.

Découpage du core Rust

  • label-registry, clearance-adapter, classified-export et durable-export-jobs.

Identité, autorisation et isolation

  • Le label est un input de décision, pas une autorisation autonome d’export.
  • La protection route/gateway et le mandat sur tech_name doivent être vérifiés de bout en bout ; non prouvés par les handlers seuls.

Exploitation et reprise

  • Binaire testé seulement sur Linux ; tests d’intégration PDP exclus par défaut selon AGENTS, aucun lancé.
  • File mémoire et BackgroundTasks ; migrations hors enforcement Alembic racine.

Séquence de migration

  • Importer labels et politiques, comparer byte/hash et décisions ; remplacer BackgroundTask par travail reprenable avec statut.
  • Rejouer matrice politique/classification/sujets ; comparer réponses et erreurs avant changement de PDP ou binaire.
  • Qualifier lecteur Arrow/Parquet sans JVM et compatibilité ZTDF ; borner les flux avant matérialisation et conserver preuves de label/édition.
  • Drainer les travaux connus, passer à une file persistée et tester reprises/cleanup avant retrait du runtime Spark.

Écarts et décisions encore ouverts

  • Le contrat propriétaire ZTDF et le remplacement du runtime .NET doivent être décidés ; encapsulation temporaire non assimilée à core Rust.
  • Le lien entre UUID label et tech_name de table doit être vérifié au contrôle d’entrée.
  • Distinguer succès d’acceptation, de chiffrement, d’upload et remise au destinataire.
