DSPF-01Cible non qualifiée

Charger la configuration SPIF et le dataset à labelliser

Comportement observé

L’application extrait un UUID de dataset de l’URL /datasets/{id}, charge son nom et les politiques. Le chargement de configuration passe par un proxy de data-model /spif-proxy/files ; il parse un XML de configuration pour récupérer les URLs SPIF puis charge et parse chaque politique. Les erreurs de chargement empêchent l’affichage du formulaire.

Utilisateurs et rôles

Gestionnaires de labels.

Interfaces dans le code

Route navigateur /datasets/{id} ; fetchConfig ; data-model /spif-proxy/files et /datasets/{id}.

Données et états

Dataset et politiques chargés dans l’état React.

Dépendances et échanges

Data-model, proxy de fichiers XML et parseur SPIF.

Comportement cible proposé

Frontends TypeScript conserve ce parcours ; IAM/Catalog fournit une politique versionnée et une édition dataset explicite.

Migration de cette capacité

Préserver formats XML et erreurs, migrer URLs backend et inclure version de politique dans la sauvegarde.

Critère d’acceptation à exécuter

Une politique XML invalide donne une erreur visible ; le nom du dataset et la politique proviennent du contexte autorisé.

DSPF-02Cible non qualifiée

Composer une classification, catégories et marques de confidentialité

Comportement observé

Le formulaire choisit une politique et réinitialise les sélections au changement. Il restaure la policy enregistrée du dataset en retrouvant classification et catégories visibles. Les sélecteurs traitent classification, contexte, ensembles de catégories, texte libre, releasability et privacy marks. Les catégories cachées ou obsolètes influent sur les options affichées.

Utilisateurs et rôles

Auteurs de labels SPIF.

Interfaces dans le code

SpifSelector ; ClassificationSelector ; ContextSelector ; CategorySelector ; ReleasabilitySelector ; PrivacyMarkSelector.

Données et états

LabelSelections : classificationLacv, categorySelections, freeTextSelections et privacyMarkSelections.

Dépendances et échanges

Modèle SPIF et policy actuelle du dataset.

Comportement cible proposé

Frontend TS conserve la composition ; la décision serveur se fonde sur la même version de politique et des identifiants stables.

Migration de cette capacité

Créer fixtures de politiques réelles anonymisées et comparer restauration des labels et changements de politique.

Critère d’acceptation à exécuter

Une sélection enregistrée est restituée à l’identique ; un changement de politique retire les sélections incompatibles sans sauvegarde implicite.

DSPF-03Cible non qualifiée

Appliquer les règles SPIF et prévisualiser le label

Comportement observé

spif-rules calcule exclusions, classifications admises, catégories requises et sélections effectives ; il détecte les conflits de contexte puis valide l’ensemble. Le formulaire calcule les issues et ne génère le label que sans erreur. Le preview affiche notamment les privacy marks et sérialise les groupes de catégories dans la syntaxe attendue par le backend. Cette validation navigateur n’est pas une autorisation serveur.

Utilisateurs et rôles

Auteurs de labels et opérateurs de politiques.

Interfaces dans le code

buildEffectiveSelections ; validateSelections ; generateLabel ; LabelPreview.

Données et états

Sélections calculées, issues error/warning et LabelOutput.

Dépendances et échanges

Parseur SPIF, règles locales et backend de label.

Comportement cible proposé

Frontends partage un contrat de validation versionné avec IAM ; le serveur Rust revalide chaque commande et trace le résultat.

Migration de cette capacité

Comparer règles client et serveur sur incompatibilités, catégories implicites et cardinalités ; n’accepter aucune divergence silencieuse.

Critère d’acceptation à exécuter

Un conflit bloque l’aperçu sauvegardable ; contourner le JavaScript ne permet pas de persister un label invalide.

DSPF-04Cible non qualifiée

Enregistrer la policy avec identité renouvelée et retour utilisateur

Comportement observé

Le bouton de sauvegarde est désactivé sans UUID valide, politique ou classification. Il envoie un PUT de policy au data-model puis affiche succès ou erreur. Axios extrait response.data et un interceptor vérifie/renouvelle le token Keycloak avant d’ajouter le Bearer ; l’option withCredentials est configurée. Le message de succès correspond à la requête de sauvegarde, pas à la preuve qu’un export chiffré a été produit.

Utilisateurs et rôles

Utilisateurs authentifiés et opérateurs.

Interfaces dans le code

PUT /datasets/{datasetId}/label/policy ; saveDatasetPolicy ; interceptor Axios.

Données et états

État isSaving, policy envoyée et retour toast ; token de session.

Dépendances et échanges

data-model, keycloak-js et configuration runtime.

Comportement cible proposé

Frontend TS remplace l’adaptateur Keycloak par OIDC sans JVM et affiche le statut durable de génération de label.

Migration de cette capacité

Préserver renouvellement, gestion d’erreur et accessibilité ; relier le toast à un reçu de commande plutôt qu’à une publication supposée.

Critère d’acceptation à exécuter

Un token expiré est renouvelé ou l’action refusée ; double-clic ne crée pas deux jobs ; succès de label et succès d’export restent distincts.

Architecture et exploitation du service cible

Plan de contrôle Rust proposé

  • Frontends TypeScript conserve ce parcours ; IAM/Catalog fournit une politique versionnée et une édition dataset explicite.
  • Frontend TS conserve la composition ; la décision serveur se fonde sur la même version de politique et des identifiants stables.
  • Frontends partage un contrat de validation versionné avec IAM ; le serveur Rust revalide chaque commande et trace le résultat.
  • Frontend TS remplace l’adaptateur Keycloak par OIDC sans JVM et affiche le statut durable de génération de label.

Plan de données proposé

  • Aucun moteur de données dans le navigateur ; lecture des politiques et commandes de sauvegarde autorisées.

Découpage du core Rust

  • Aucun frontend Rust requis ; cœur serveur label/validation en Rust, contrat TS généré et adaptateur OIDC.

Identité, autorisation et isolation

  • Le navigateur ne tranche ni clearance ni droit d’export ; serveur autoritaire.
  • Validation et chargement XML ne doivent pas autoriser une URL interne arbitraire via le proxy.

Exploitation et reprise

  • Application Vite/bun ; état local React et configuration runtime ; aucun test UI exécuté.

Séquence de migration

  • Préserver formats XML et erreurs, migrer URLs backend et inclure version de politique dans la sauvegarde.
  • Créer fixtures de politiques réelles anonymisées et comparer restauration des labels et changements de politique.
  • Comparer règles client et serveur sur incompatibilités, catégories implicites et cardinalités ; n’accepter aucune divergence silencieuse.
  • Préserver renouvellement, gestion d’erreur et accessibilité ; relier le toast à un reçu de commande plutôt qu’à une publication supposée.

Écarts et décisions encore ouverts

  • L’UI présente des privacy marks, mais la policy envoyée contient policy/classification/category : caractériser leur représentation attendue dans le contrat serveur.
  • Version de politique et édition dataset non explicites dans le parcours lu ; à ajouter.
