1 Résumé exécutif & constats

Ce qui tourne aujourd'hui, les faits vérifiés dans le code, et les quatre défauts structurels.

Un dataflow naît dans data-dev (atelier low-code) qui génère un script (PYSPARK, PYTHON ou SQL) déposé dans MinIO. process-data l'exécute dans une session selon deux runtimes : les sessions PySpark passent par Lighter (REST Livy/Sparkmagic, Spark 3.3.4, Py4J Gateway) ; les sessions Python sont des pods python-runner (FastAPI) pilotés directement via l'API Kubernetes. Le script lit/écrit les datasets du lakehouse Iceberg (catalogue REST cleyrop) via le SDK client-python — la même couche qu'utilisent les notebooks JupyterLab. L'ingestion (E/L) vit à part dans data-collect (connecteurs SFTP·JDBC·API…, exécution in-process, Quartz non clusterisé).

Quatre défauts structurels motivent la cible : ① trois dépôts d'état (DB process-data · DB Lighter · K8s) réconciliés à la main → zombies & reboots sales (§4) ; ② un moteur figé et couplé — Lighter en 3.3.4 alors que le runtime est en 4.1.2, un driver lourd par session (§6) ; ③ des credentials S3 statiques, larges, partagés — l'autorisation n'est appliquée ni au catalogue ni au stockage (§8) ; ④ ni gestion de datasets ni lignage — les tables Iceberg sont écrites « à nu » : pas d'environnements, pas d'audits bloquants, pas de provenance exploitable (Parties V–VI).

Constats vérifiés (juin 2026, code faisant foi) : ① Le runtime d'exécution est déjà en Spark 4.1.2 (image dataflow-spark-runner ; le README resté à 3.5.8 est obsolète) ; seul Lighter traîne à 3.3.4. ② Les sessions Python sont déjà K8s-natives (Deployment/Service + FastAPI), sans Lighter. ③ Le SDK client-python acquiert Spark via getOrCreate() (compatible Connect) sauf deux usages RDD/SparkContext à réécrire (§5). ④ Le catalogue est iceberg-rest-catalog type REST, aussi lu par Trino (la mention « Nessie » du README runner est obsolète). ⑤ Le proto Kafka SessionEvent/ClusterEvent ne porte pas d'endpoint (champ à ajouter). ⑥ Le cluster exploite déjà des opérateurs (Strimzi, Keycloak) — le pattern est établi.

6 L'apport de Spark Connect

Ce qu'un moteur découplé change concrètement pour Hemera.

Spark Connect (GA en 3.5, présent dans notre 4.1.2) sépare l'application du moteur : un client léger (pyspark[connect], sans JVM) construit un plan DataFrame et l'envoie en gRPC/Protobuf à un serveur Spark distant (sc://…:15002) qui l'optimise (Catalyst), l'exécute et renvoie les résultats en Arrow. Les UDF voyagent en cloudpickle, les dépendances via addArtifacts. L'enjeu n'est pas d'adopter une nouveauté : c'est de remplacer la pile Lighter + Py4J (un driver couplé par session, figé en 3.3.4) par un moteur mutualisé que tout le reste — dataflows, notebooks, services, SDK — consomme comme un service réseau.

🗑️
Lighter disparaît

Un service entier retiré, son Py4J Gateway, son modèle session/statement — et son 3e dépôt d'état, source des zombies (§4).

🪶
Driver mutualisé

Fini « 1 driver lourd par session » : un serveur sert N sessions logiques, alloue les executors dynamiquement, supprime le polling de pods.

🐍
Substrat Python unifié

Tout job Python tourne dans python-runner ; un job PySpark = le même pod en client sc://. Un seul substrat d'exécution.

✂️
data-dev simplifié

cloudpickle capture la closure des UDF : fin de la chirurgie d'imports (extractLibImport) ; les InternalModule deviennent des fichiers addArtifacts(pyfile=True).

🧪
Notebooks & services allégés

JupyterLab et datasphere cessent d'embarquer une distribution Spark : clients sc:// légers, démarrage rapide, même moteur & catalogue que les dataflows.

🐞
Debug hors cluster · versions découplées

Un script client Python pur se débogue depuis un IDE/CI en pointant sc:// ; client et serveur évoluent séparément ; une session qui plante n'emporte plus les autres.

La seule vraie limite : Spark Connect couvre l'API DataFrame / SQL / Functions — pas RDD, SparkContext ni py4j direct. Concrètement : corriger les 2 points du SDK (§5) et auditer les transformations Python avancées générées par data-dev. La quasi-totalité des dataflows DataFrame/SQL passe sans modification.

9 Lakekeeper : authz au catalogue + accès S3 délégué

Centraliser la gouvernance là où vit la donnée : le catalogue décide ET délègue l'accès S3. Validé par le PoC spark-lakekeeper-auth.

Lakekeeper est un catalogue Iceberg REST (Rust) qui ajoute : (1) une autorisation fine intégrée via OpenFGA (warehouse → namespace → table) liée à l'identité OIDC/Keycloak — réutilisant le moteur ReBAC déjà en place au gateway ; (2) l'accès S3 délégué (X-Iceberg-Access-Delegation) : après vérification de la politique, le client reçoit soit des credentials temporaires scopés (backends à STS — AWS/MinIO), soit du remote-signing (Lakekeeper signe chaque requête — le cas OVH & Outscale, sans STS). Le même mécanisme sert le serveur Spark Connect et les clients PyIceberg.

Machine à états d'un job — anti-zombie par construction

QUEUED → LEASED → RUNNING → SUCCEEDED ; FAILED → retry (backoff, < N) puis descendants SKIPPED. Un seul registre : la file Postgres. Crash orchestrateur ⇒ au reboot il relit la file, rien à reconstruire. SUCCEEDED = snapshot Iceberg publié présent.

16 Write-Audit-Publish : la publication gardée par les audits

Aucune donnée ne devient visible sans avoir passé ses audits — pour tous les nœuds, tous les moteurs.

Le commit Iceberg est atomique, mais l'atomicité ne dit rien de la qualité : un run qui écrit des données fausses les publie atomiquement. Le draft avait des nœuds TEST et les audits SQLMesh — après ou à côté de l'écriture. La v2 fait des audits une garde de publication, uniforme pour tous les nœuds (SQL, @step, SOURCE, op IA), via le pattern WAP natif Iceberg :

1 WRITE — isolé
brancher wap depuis la tête de l'environnement, écrire dessuscreate_branch(env_head, "wap") puis overwrite(df, branch="wap") (full) ou upsert(df, join_cols=keys, branch="wap") (merge incrémental) — les lecteurs de main/env_dev ne voient rien
2 AUDIT — sur exactement ce qui serait publié
scanner la branche wap · évaluer les audits du nœudnot_null · unique · accepted_values · row_count_at_least · expression(…) — déclarés sur @step(audits=…), en MODEL(audits …) SQLMesh, ou en YAML de nœud SOURCE. Un échec ⇒ exception.
3 PUBLISH — ou abort, jamais entre les deux
✓ audits OKfast-forward de la branche d'environnement sur la tête de wap · drop wap · job SUCCEEDED
✗ audit KOdrop wap — l'environnement n'a pas bougé · job FAILED (retry/SKIPPED §14) · rien à nettoyer
Correspondance moteurs : PyIceberg/DuckDB/Polars = manage_snapshots() + écritures par branche (validé §15) ; Spark = spark.wap.branch / write.branch() + procédure fast_forward ; SQLMesh = ses audits bloquants, raccordés à la même branche. Le mécanisme vit une fois, dans lake.write() — aucun step ne peut « oublier » le WAP.

def write(self, df, dataset, env, mode, keys, audits, provenance):
    tbl = catalog.load_table(dataset); head = tbl.snapshot_by_name(branch_of(env))
    tbl.manage_snapshots().create_branch(head.snapshot_id, "wap").commit()      # 1. WRITE (isolé)
    (tbl.upsert(df, join_cols=keys, branch="wap", snapshot_properties=provenance)   # merge idempotent
        if mode == "merge" else
     tbl.overwrite(df, branch="wap", snapshot_properties=provenance))            # + provenance §20
    staged = tbl.scan(snapshot_id=tbl.snapshot_by_name("wap").snapshot_id).to_arrow()
    try:
        run_audits(dataset, audits, staged)                                     # 2. AUDIT — veto par exception
    except AuditError:
        tbl.manage_snapshots().remove_branch("wap").commit(); raise            # l'env n'a jamais bougé
    fast_forward(tbl, branch_of(env), to="wap")                                 # 3. PUBLISH — atomique
    tbl.manage_snapshots().remove_branch("wap").commit()

18 Schéma : évolution sur branches, WAP & snapshots — time travel, maintenance

Le point le plus subtil du modèle : le schéma Iceberg n'est PAS isolé par branche. Comportement vérifié empiriquement, et le protocole qui en découle.

Le fait qui gouverne tout le reste : dans Iceberg, le schéma est une métadonnée de table (liste de schemas[] + un current-schema-id global). Les branches sont des refs vers des snapshots ; chaque snapshot enregistre le schema_id avec lequel il a été écrit — mais update_schema() est un commit de métadonnées global, immédiat, sans snapshot : il est visible de tous les lecteurs de main à l'instant même, même si « on travaillait sur la branche dev ». Le WAP et les branches n'isolent que les données — jamais le schéma. Toute la gestion de schéma doit donc être conçue autour de ce fait, pas contre lui.

Le modèle à trois plans — un schéma n'est pas « un » schéma

① Contrat (manifeste)le schéma déclaré par version de flow — versionné au build, diffé par le plan, revu en MR. C'est l'intention.
② Physique courant (table Iceberg)current-schema-id — global, partagé par toutes les branches. Modifié uniquement par une migration ordonnée par le plan. C'est l'état.
③ Historique (par snapshot)chaque édition porte son schema_id — le time travel projette le schéma d'époque. C'est la mémoire.
Les trois plans divergent légitimement pendant une transition : le contrat v7 peut retirer une colonne alors que le physique la garde (contraction différée), et les éditions anciennes la montreront pour toujours. L'UI doit montrer les trois, jamais les confondre (écran S3 du design frontend).

Règles dérivées — appliquées partout

🚫
Jamais d'auto-évolution

lake.write() n'a pas de mode « mergeSchema » : un dataframe qui ne matche pas le contrat = erreur de build/run, pas une mutation silencieuse du schéma global. Un update_schema émis hors plan (client direct) est capté par les change events Lakekeeper → Catalog → alerte « schéma sauvage » (§21).

🆔
Le field-id est l'identité

Catalog, labels PII et lignage colonne sont clés par (table, field-id) : un rename conserve lignage et labels automatiquement (F5) ; une colonne ré-créée du même nom (F4) est un nouvel objet — pas d'héritage de label, re-classification requise. C'est une propriété de sécurité, pas une gêne.

🔎
Le build attrape les références mortes

Audits, ref() aval et column_map qui référencent une colonne retirée du contrat échouent au build (plan), jamais au run. Le plan en MR montre le diff de schéma par colonne, croisé avec l'impact aval réel (lignage colonne du Catalog).

🧭
Une seule sémantique de lecture, affichée

Convention plateforme, encodée dans lake et l'UI : édition (snapshot/tag) = schéma d'époque (F2) ; tête d'environnement = schéma courant. Attention inter-moteurs : Spark lit une branche avec le schéma courant, un snapshot avec le schéma d'époque ; PyIceberg vérifié idem sur snapshot — la parité Trino est un point de la checklist d'intégration.

Approfondissement (spike n°2, F9–F16 — annexe dédiée « Gestion de schéma Iceberg ») : types imbriqués = field-ids à tous les niveaux, diff récursif au plan · couplages vérifiés : drop d'une colonne source de partition ou d'un identifier field rejeté par Iceberg → migrations composites ordonnées (détacher le spec/l'identifiant d'abord) · tolérance d'écriture : une colonne optional manquante s'écrit en NULL sans erreur → lake.write() fait un contrôle de contrat strict (la régression silencieuse devient une erreur) · le snapshot estampille le schéma courant au commit · rollback vérifié : restaure les données, pas le schéma (contre-migration explicite) · commits de schéma concurrents = CommitFailedException → sérialisation par table + retry-rebase dans l'orchestrateur · piège v2 : PyIceberg accepte des default values hors-spec sur v2 (les autres moteurs les ignoreraient) → défauts interdits au build jusqu'à v3 uniforme · union_by_name = primitive expansion-only (n'exécute jamais un drop) · sémantique de lecture de branche divergente entre moteurs (Spark = schéma courant) → convention unique encapsulée dans lake. 21 Le Cleyrop Catalog — source de vérité des objets

Un service Cleyrop dédié qui matérialise le graphe complet de la plateforme — alimenté par les événements OpenLineage des workers ET par les change events de Lakekeeper.

Les workers émettent de l'OpenLineage (standard ouvert du lignage d'exécution : run/job/datasets + facettes, adopté par Airflow, Spark, dbt, Dagster) — mais ces événements ne restent pas dans Flows : ils alimentent un service dédié, le Cleyrop Catalog (apps/catalog, Python/FastAPI + Postgres), qui devient la source de vérité de tous les objets de la plateforme : datasets et leurs éditions (snapshots), flows et versions, runs et jobs, sources/connecteurs, schémas et leurs versions, colonnes, labels/classification, propriétaires, modèles IA utilisés.
