1 Le modèle : où vit le schéma, vraiment

Quatre objets, quatre durées de vie — tout le reste est une conséquence.

Métadonnées de table (globales — un seul exemplaire, toutes branches confondues)schemas[] : l'historique complet des schémas, chacun avec son schema-id · current-schema-id : LE schéma courant · last-column-id : compteur de field-ids, jamais réutilisé · partition-specs[], sort-orders[] : référencent les colonnes par field-id · identifier-field-ids : l'identité de ligne (upsert)
▼ chaque commit de données produit…
Snapshotimmuable · estampille le schema-id courant au moment du commit (F13) · pointé par les refs
Refs (branches & tags)de simples pointeurs vers des snapshots — ne portent aucun schéma
Fichiers de donnéescolonnes identifiées par field-id dans Parquet · jamais réécrits par une évolution — la projection fait tout
Corollaire : update_schema() est un commit de métadonnées (pas de snapshot, pas de branche) → global et immédiat pour tous les lecteurs « courants ». La lecture d'un snapshot précis projette son schéma d'époque ; la lecture d'une tête de branche projette le schéma courant. Les fichiers ne bougent jamais : ajout → NULL comblé à la lecture, drop → colonne ignorée, rename → résolution par field-id.

3 Types imbriqués : des field-ids à tous les étages F9 vérifié

struct, list, map évoluent comme le niveau racine — chaque champ imbriqué a son propre field-id.

Vérifié : add_column(("addr","country")) ajoute un champ dans un struct ; rename_column(("addr","zip"), "postcode") renomme un champ imbriqué. Les field-ids sont attribués à chaque niveau (racine : 1–3 ; champs du struct : 4, 5, 7 — le compteur est global à la table) et les anciennes lignes se relisent avec le champ ajouté à None : {"city": "Paris", "postcode": "75001", "country": None}. Les éléments de list/map ont aussi leurs ids (element, key, value).

🌳
Conséquence Catalog

Le modèle « colonne » du Catalog est en réalité un arbre de champs : clé = (table, field-id), avec un chemin (addr.postcode) qui peut changer par rename. Labels PII et lignage s'attachent au field-id feuille — un label sur addr.country ne couvre pas tout le struct.

🪜
Conséquence contrat/plan

Le diff de schéma du plan doit descendre récursivement dans les types imbriqués : ajouter un champ dans un struct est une expansion ; en retirer un est une contraction — mêmes règles de différé qu'au niveau racine.

4 Couplages : partition, tri, identifiants F10–F11 vérifiés

Le schéma n'évolue pas seul : specs de partition, ordres de tri et identifiants de ligne le référencent par field-id.

Pour le plan : le compilateur classe une migration touchant une colonne référencée (partition, tri, identifiant, — et par extension : audits, column_map, lignage aval) comme composite : elle se décompose en étapes ordonnées (détacher la référence → migrer → rattacher le cas échéant), affichées telles quelles dans l'écran S14. Iceberg refuse de toute façon le mauvais ordre — le plan le rend juste visible et volontaire.

5 Tolérance d'écriture ≠ respect du contrat F12 vérifié

Iceberg est laxiste à l'écriture — c'est une feature pour lui, un risque pour nous. Le contrat doit être vérifié au-dessus.

Écriture testéeIceberg (PyIceberg)Risque plateforme
Dataframe sans une colonne optionalACCEPTÉ — la colonne vaut NULLrégression silencieuse : un step qui cesse d'alimenter une colonne publie des NULL sans erreur
Colonnes dans un ordre différentACCEPTÉ — résolution par nom/field-idaucun
Arrow int32 dans une colonne longACCEPTÉ — up-cast à l'écriturefaible — mais le contrat doit noter le type logique, pas le type d'arrivée
Colonne inconnue du schémaREJETÉ (F8)aucun — c'est la barrière qui impose l'ordre expansion→write
Règle majeure (nouvelle) — le contrôle de contrat à l'écriture : lake.write() compare le schéma du dataframe au contrat du nœud (pas seulement au schéma Iceberg) en mode strict : colonne du contrat absente du dataframe = erreur, sauf si le plan l'a explicitement marquée « en cours de retrait » (contraction pendante, où les NULL sont attendus côté dev). Sans ce contrôle, la tolérance d'Iceberg transforme un bug de transformation en corruption silencieuse — que seuls des audits not_null exhaustifs rattraperaient par accident.

6 Estampillage des snapshots & rollback F13 vérifié

Ce que « le schéma d'une édition » veut dire exactement — et ce qu'un rollback restaure (et ne restaure pas).

🏷️
Le snapshot estampille le schéma courant au commit

Vérifié : après une expansion, un write sans la nouvelle colonne produit quand même un snapshot marqué du nouveau schema_id. Le « schéma d'une édition » (S4) = l'état du schéma à la publication, pas la forme du dataframe écrit. Cohérent — et une raison de plus pour le contrôle de contrat (§5).

⏪
Le rollback restaure les données, pas le schéma

Vérifié : rollback_to_snapshot(old) ramène la ref sur l'ancien snapshot, mais current-schema-id garde les évolutions postérieures. Lire la tête après rollback = anciennes données projetées dans le nouveau schéma (colonnes ajoutées → NULL). Si le contrat doit reculer aussi : contre-migration explicite (proposée par l'UI S4), qui n'est possible que si rien d'autre ne référence les colonnes ajoutées.

7 Concurrence des commits de schéma F16 vérifié

Deux évolutions simultanées : l'optimisme d'Iceberg, et la sérialisation que le runner doit ajouter.

Vérifié : deux clients chargent la table, chacun fait un update_schema ; le second échoue en CommitFailedException: Requirement failed: current schema id has changed (expected 1, found 2). Le commit de métadonnées est optimiste avec pré-condition — pas de merge automatique de deux évolutions concurrentes dans PyIceberg (le client doit recharger et rejouer).

🔒
Règle runner

Les migrations de schéma d'une table sont sérialisées par l'orchestrateur (la file sait déjà sérialiser par dataset pour le WAP §16 archi) + retry avec rebase : recharger les métadonnées, revalider que la migration est toujours pertinente (le diff peut avoir été appliqué par un autre run du même plan), rejouer. Les migrations étant déclaratives (issues du contrat), le rejeu est idempotent.

🧷
Écriture vs migration

Un write de données pendant une évolution de schéma est sûr : le write valide son shape contre le schéma au commit et échoue proprement s'il est devenu incompatible (F8) — jamais d'état mixte. Le pire cas est un retry, pas une corruption.

8 Format v3, valeurs par défaut — et un piège v2 bien réel F14 vérifié — piège

Les default values débloqueront les ajouts required — mais aujourd'hui la zone est dangereuse.

Le futur (spec v3) : chaque champ peut porter initial-default (valeur projetée sur les lignes antérieures à l'ajout) et write-default (valeur si le writer omet la colonne). Cela rend l'ajout d'une colonne required légal et sûr — l'expansion la plus demandée. v3 apporte aussi de nouveaux types (variant, geometry…) et le row lineage natif.

Le présent, vérifié : ① PyIceberg 0.11 refuse d'écrire des tables v3 (« Writing V3 is not yet supported », issue apache/iceberg-python#1551) ; ② mais il accepte add_column(required=True, default_value=…) sur une table v2, et écrit initial-default/write-default dans le JSON de métadonnées en format-version 2 — hors spec. Son propre lecteur les honore (les vieilles lignes rendent « N/A », vérifié jusque dans le fichier de métadonnées) ; un autre moteur lisant cette table v2 (Spark/Trino) peut légitimement les ignorer → la même table rend "N/A" ici et NULL (sur une colonne required !) ou une erreur là-bas.

Actualisation 02/07/2026 : côté Java/moteurs, la donne a changé — Iceberg 1.11.0 (mai 2026) déclare le feature set v3 « production-ready » (DV, Variant, géo, ns) et v3 est GA sur les principales plateformes au S1 2026. PyIceberg (0.11.1, toujours la dernière release) est désormais LE goulot : les conditions de levée ① et ④ ci-dessous restent bloquantes, ②/③ se rapprochent.

Règle plateforme (R11, précisée) : les valeurs par défaut sont interdites (garde au build) et le lakehouse est épinglé en format-version 2. Comme PyIceberg bloque lui-même écriture et upgrade v3, le risque immédiat n'est pas nos workers — c'est un upgrade par un autre moteur (Spark saura le faire avant Python) qui rendrait la table illisible/inécrivable par la moitié de la plateforme. Donc : le format-version est une propriété gérée par la plateforme — verrouillée côté Lakekeeper (politique sur upgrade-format-version), un upgrade sauvage étant détecté par les change events → alerte Catalog. Conditions de levée (toutes) : ① release PyIceberg fermant #1551 avec DV write ; ② v3 GA (pas preview) sur Spark et Trino de la matrice ; ③ Lakekeeper validé sur métadonnées v3 ; ④ test d'intégration multi-moteurs vert sur une table v3 avec defaults + DV. La migration se fera alors table par table, par un flow système, jamais implicitement.

9 union_by_name : la primitive de calcul des migrations F15 vérifié

Expansions automatisables, contractions jamais implicites — exactement la asymétrie du protocole expand/contract.

Vérifié : update_schema().union_by_name(nouveau_schema) ajoute les colonnes manquantes (avec de bons field-ids), et — crucial — un union avec un schéma plus petit ne supprime rien : les colonnes absentes sont conservées. La primitive est donc expansion-only par construction : parfaite pour appliquer la partie « expand » d'un plan, structurellement incapable d'exécuter une contraction par accident.

Calcul des migrations au plan — le diff de contrat se décompose ainsi

def compute_migrations(contract_old, contract_new) -> Migrations:
    return Migrations(
        expansions   = diff_additive(contract_old, contract_new),   # add optional (union_by_name) · rename (par field-id) · widen · required→optional
        contractions = diff_destructive(contract_old, contract_new), # drop · narrow · optional→required — TOUJOURS explicites, différées à la promotion
        composites   = order_references(contractions),               # § 4 : détacher partition/tri/identifiants d'abord
    )
# apply (env)   : apply_expansions() PUIS écriture WAP (F8)
# promote (prod): fast-forward des refs PUIS apply_contractions() — code prod déjà migré (§18 archi)

10 Name-mapping & fichiers importés règle spec — à couvrir en test d'intégration

Le cas des données qui n'ont pas de field-ids : imports de Parquet existants par l'ingestion.

Toute la mécanique de ce document repose sur les field-ids dans les fichiers. Or un Parquet écrit hors Iceberg (import direct add_files, migration d'un lac existant) n'en a pas. Iceberg couvre ce cas avec la propriété schema.name-mapping.default : une table de correspondance nom→field-id utilisée en repli à la lecture. Conséquences pour Hemera : (1) les connecteurs d'ingestion qui réécrivent les données (le chemin normal : write via lake) produisent des fichiers avec field-ids — aucun sujet ; (2) un éventuel chemin « adoption sans copie » (add_files) doit obligatoirement poser le name-mapping à la création, sinon renames et drops ultérieurs liront de travers ; (3) après adoption, tout rename côté source ne doit plus jamais être répercuté par nom — le mapping fige la correspondance historique.

Décision associée : le chemin par défaut de l'ingestion Hemera est la réécriture gouvernée (WAP, provenance, field-ids propres). add_files/adoption sans copie est une optimisation réservée aux gros volumes migrés une fois, avec name-mapping posé et vérifié par un test d'intégration dédié (ticket DS/annexe dans E5).

11 Matrice moteurs — vérifié vs à vérifier

La sémantique de lecture n'est pas un détail d'implémentation : elle fait partie du contrat de la plateforme.

La divergence qui compte : « lire l'environnement dev » via Spark (branche = schéma courant) et via lake/PyIceberg (head par snapshot-id = schéma du head) peut différer pendant une transition de schéma. La plateforme tranche : lire un environnement = lire la tête de sa branche avec le schéma courant (aligné Spark) ; lire une édition = schéma d'époque. lake encapsule cette convention pour tous les moteurs, et le test d'intégration multi-moteurs (Spark/Trino/PyIceberg lisant la même table en transition) est un gate de la checklist E3.

DRAFTdiff contrat vN→vN+1 calculé au build (expansions · contractions · composites ordonnés)
