2 Le contrat d'édition & les deux PEP — ce qui rend un objet gouvernable généralisation

L'hypothèse attaquée : « le hand-off inter-nœuds = toujours une table Iceberg ». Verdict : l'hypothèse tombe, les invariants restent — un seul contrat d'édition, deux points d'application de l'autorisation.

Le principe de généralisation — un contrat d'ÉDITION, deux points d'application

Ce qui rend les tables gouvernables, ce ne sont pas les lignes : c'est le contrat d'édition — ① des éditions immuables et identifiées, ② une publication atomique et gardée par des audits (le WAP, quel que soit son mécanisme), ③ une provenance portée par l'édition (run, code, entrées épinglées), ④ un rollback = repointer. Tout type d'objet doit honorer ce contrat — mais pas forcément via une table Iceberg. Et l'autorisation a deux points d'application (PEP), un par famille :

EMBEDDINGS vs EXPORT — calculer & servir vs déménager

🧲
EMBEDDINGS = un DATASET

Il produit des données : une table Iceberg de vecteurs, avec éditions, WAP, audits (dim, drift, recall@k), lignage (chunks ← fichiers ← corpus + le modèle d'embedding en code). C'est une vérité versionnée — et elle est servie : le service Embeddings matérialise chaque édition en collection dans le backend choisi (Qdrant, Milvus, pgvector…) et l'expose derrière un alias — publier = basculer l'alias, rollback = le repointer. Les apps appellent le proxy, jamais le store.

📤
EXPORT = une SYNCHRONISATION

Il ne produit rien : il fait habiter une édition épinglée d'un dataset dans un système de service non versionné qu'on ne peut pas proxyfier (cache Redis, CRM, API push, dépôt partenaire). Pas d'édition propre, pas de WAP — juste l'idempotence « cible = dataset@édition » et un état de sync journalisé. Détruire la cible ne perd rien : re-sync = rejouer l'édition.

En une phrase : EMBEDDINGS calcule ET sert (via le proxy), EXPORT déménage — et on ne déménage que ce qu'on ne peut pas servir. La chaîne RAG n'a plus besoin d'EXPORT : app → service Embeddings (proxy) → backend. Les credentials des stores vivent côté service — jamais dans les apps, jamais dans les steps ; chaque requête passe la décision OpenFGA (can_read(user, dataset)) et se journalise comme consommation dans le lignage. Corollaire : changer de backend (Qdrant → Milvus) est une opération de placement — aucune app ne change. L'EXPORT reste pour le reste : pousser une table vers un CRM, déposer un extract chez un partenaire.

Les services Cleyrop existants = les exécuteurs des kinds alignement produit

🗄️
Service « Files » (S3) → le PROPRIÉTAIRE du kind FILESET

Le pattern existant s'applique tel quel : APISIX + OpenFGA devant, métadonnées dans son Postgres, blobs S3 adressés par contenu. Il lui manque une seule chose pour honorer le contrat d'édition : des manifestes d'édition immuables (édition N = liste {hash, nom, méta} + provenance) avec publication atomique gardée par les audits (mime/scan/dédup) — le WAP version service. Le presign vérifie OpenFGA (l'API est le plan de données), le GC est un refcount local, et chaque édition publiée part en événement au Catalog. La table d'index Iceberg devient une option (si on veut du SQL sur le corpus), plus un prérequis.

🧲
Service « Embeddings » → le PROXY de serving du kind EMBEDDINGS

Même pattern : APISIX + OpenFGA devant, et dans son Postgres le mapping dataset → backend/collection ainsi que les credentials des stores (Qdrant, Milvus, pgvector… — jamais dans les apps, jamais dans les steps). La table Iceberg de vecteurs reste la vérité (le SQL dessus est une feature, produite par le DAG) ; le service matérialise chaque édition en collection, expose des alias (promote = bascule atomique, rollback = repointage) et sert toutes les requêtes : décision OpenFGA par requête, routage backend, journalisation en consommation de lignage. Multi-stores, zéro credential dans les apps, backend interchangeable sans changement d'application.

Ce qui n'est PAS un dataset (décision) : les prompts, configs de modèles et hyperparamètres sont du code — versionnés dans le repo, fingerprintés dans le manifeste (un prompt modifié ⇒ nœud sale ⇒ rebuild), tracés dans la provenance (prompt_hash, déjà prévu §20 archi). Les mettre « en base » casserait le plan : un changement de prompt doit passer par une MR, pas par un UPDATE.

La règle de visibilité — l'ancrage Iceberg est un détail d'implémentation règle V1–V3

L'objection à traiter : « tout est backé par des tables Iceberg — un client qui parcourt son catalogue via Trino va voir des tables d'index, des métriques de modèles, du state SQLMesh mélangés à ses datasets ». L'ancrage est un choix de mécanique (une seule implémentation d'éditions/WAP/authz pour tous les types — vs N systèmes de versionnage) ; il ne doit jamais devenir l'expérience du client. Trois règles :

#RègleMise en œuvre
V1Namespaces système séparés — les ancrages (index de filesets, métriques de modèles, state des régions, staging) vivent sous _hemera.* (option : warehouse Lakekeeper dédié)les montages Trino/Spark clients n'exposent que les namespaces métier — un SHOW TABLES ne montre jamais un ancrage
V2La navigation client = le Catalog métier, pas le listing Iceberg — on montre des objets (corpus, modèle, index vectoriel) avec leurs fiches« ancrage : table d'index (système) » n'apparaît que dans un panneau avancé des fiches S27–S29
V3L'authz garantit ce que la convention prometaucune relation read OpenFGA sur _hemera.* pour les utilisateurs ; accès via les API d'objet uniquement (lake.fileset, registry, service Files)

Et la frontière visible/caché est un choix par kind, tranché par « le SQL dessus est-il une feature ? » : TABLE/VIEW/INCREMENTAL, FEATURESET et EMBEDDINGS (requêter vecteurs/métadonnées en SQL est utile) = tables métier visibles ; FILESET et MODEL = objets de service, consommés via leurs abstractions. Précédent industriel : volumes et modèles Unity Catalog sont des securables du même metastore que les tables — l'UX nomme, personne n'est dérouté. Note : avec le modèle « PEP service » (§ précédent), les objets médiés par un service (filesets, poids de modèles) n'ont même plus besoin d'ancrage dans le catalogue Iceberg — la question de la pollution disparaît à la racine pour eux ; V1–V3 ne s'appliquent qu'aux ancrages restants (option SQL, staging, state de régions).

Verdict du challenge : la taxonomie s'ouvre sans casser l'uniformité — un DAG, une syntaxe (MODEL()/@step, mêmes audits(…)), un moteur de publication (WAP sur l'ancrage Iceberg), un registry (le Catalog — éditions pour tables, corpus, modèles, vecteurs, features), et les services Cleyrop existants comme exécuteurs (files → FILESET, embeddings → proxy de serving des EMBEDDINGS) plutôt que des systèmes parallèles. Couverture validée contre Unity Catalog et DataHub : chaque type d'objet de l'écosystème est soit un dataset à éditions, soit du code fingerprinté, soit un consommateur d'éditions, soit de l'organisation — mêmes lignage et autorisation partout. Tickets : FS-1 (kind FILESET + lake.fileset via service files), FS-2 (contrat GC Catalog↔files), ML-1 (kind MODEL + registry Catalog), ML-2 (wrap MLflow), EM-1 (kind EMBEDDINGS + service proxy multi-stores : collections par édition, alias), EM-2 (query-plane du proxy : perfs, matrice de capacités des backends), FT-1 (FEATURESET + audit point-in-time), ST-1 (STREAM + bridge ACL Kafka↔OpenFGA), INT-15 (presign du service files sous décision OpenFGA).

5 La syntaxe native — SQLMesh-first, idiomes dbt acceptés S1 · S2 validées

Le choix : la forme MODEL() de SQLMesh comme base (SQL pur, zéro templating obligatoire), et un shim qui accepte les habitudes dbt dans le même fichier.

Pourquoi SQLMesh-first et pas dbt-first ? Trois raisons techniques : ① la forme SQLMesh est du SQL pur + un en-tête déclaratif — parseable, transpilable, lignage colonne par AST — là où dbt est du Jinja avant d'être du SQL (le SQL n'existe qu'après rendu) ; ② SQLMesh infère les dépendances des noms de tables (vérifié S1b), exactement comme notre compilateur — dbt a besoin de ref() parce que Jinja ne voit pas le SQL ; ③ les audits sont déclarés dans le modèle, pas dans un YAML à côté — aligné avec notre garde WAP. Mais un DE dbt ne doit rien réapprendre : le shim (S2) accepte {{ ref() }}, {{ source() }}, {{ config() }}, {% if is_incremental() %}, {{ this }}, {{ var() }} — et les normalise vers le même IR en ~30 lignes de rendu Jinja contrôlé (vérifié : config capturée, refs résolus, SQL rendu parseable, IR identique).

Le même modèle, écrit dans les deux styles — un seul IR à l'arrivée

-- Style A (canonique — SQLMesh) ------------------------------- transformations/fct_sales.sql
MODEL (name fct_sales, kind INCREMENTAL_BY_TIME_RANGE (time_column order_date),
       grain order_id, cron '@daily', audits (not_null(columns := (order_id))));
SELECT o.order_id, o.order_date, o.amount * fx.rate AS amount_eur
FROM orders_clean o JOIN fx_rates fx ON o.currency = fx.currency     -- deps inférées des noms (S1b)
WHERE o.order_date BETWEEN @start_ds AND @end_ds

-- Style B (habitudes dbt — le shim, S2) ------------------------ même fichier .sql accepté
{{ config(materialized='incremental', unique_key='order_id', audits=['not_null(order_id)']) }}
select o.order_id, o.order_date, o.amount * fx.rate as amount_eur
from {{ ref('orders_clean') }} o join {{ source('crm','fx_rates') }} fx on o.currency = fx.currency
{% if is_incremental() %} where o.order_date > (select max(order_date) from {{ this }}) {% endif %}

Comment c'est compilé — S1 a validé le cœur (décision D1-b)

⚙️
SQLMesh en bibliothèque, sans état

Vérifié S1 : load_sql_based_model() parse le MODEL, infère les deps sans ref(), extrait les audits, et render_query(start, end) substitue la fenêtre — aucun Context, aucune state DB, aucun environnement virtuel touché. Et le même modèle se rend en dialecte spark (prod) et duckdb (dev) — le contrat des gateways tient.

🩹
Le shim dbt avant parse

Vérifié S2 : un environnement Jinja contrôlé (6 symboles : config/ref/source/is_incremental/this/var — liste fermée) rend le style B vers du SQL pur + une config capturée. Un fichier utilisant un symbole hors liste (macro de package, run_query…) = erreur de build avec message : « ceci nécessite le mode wrap dbt ».

La frontière du natif, dite franchement : pas de macros custom, pas de packages dbt, pas de macros Python SQLMesh en mode natif — c'est la ligne qui garde le natif parseable, transpilable et lignagé colonne par colonne. 8 Le SDK lake — un objet Python par kind, le cycle de vie complet conception

La critique reçue : lake savait manipuler des tables Iceberg, pas les 9 kinds. La réponse : un contrat de base unique (DatasetHandle + stage()), un handle typé par kind qui n'ajoute que ses spécificités, et le destructif gouverné par construction.

Règle de conceptionConcrètement
R-SDK-1 · stage() est LA primitive d’écriturele WAP généralisé : branche Iceberg (tables, vecteurs, features, atterrissage stream), manifeste staging + blobs pending (filesets), version pending (modèles). publish = repointage atomique après audits, partout ; veto ⇒ rien n’existe. Aucune méthode write() hors staging.
R-SDK-2 · un contrat de base, des handles typéstout code écrit contre DatasetHandle (éditions, rollback, grants, lignage, rétention) marche pour les 9 kinds ; un handle typé ajoute ce qui est propre au kind, ne retire jamais rien.
R-SDK-3 · lecture = adressage par éditionds.pin(), ds.at(ts), ctx.inputs auto-épinglés : toute lecture est reproductible, la provenance s’écrit toute seule.
R-SDK-4 · les deux PEP sont invisibles dans l’APImême verbe, chemin différent : t.read() = Iceberg remote-signé (PEP 1) ; f.url() = presign du service Files après décision OpenFGA (PEP 2) ; e.query() = service Embeddings au query-time. Le SDK choisit le chemin, jamais l’utilisateur.
R-SDK-5 · le destructif est gouvernédrop, purge, contraction de schéma, promote : en prod ⇒ PlanRequired (plan/apply, MR, revue) ; direct seulement en environnement de dev. Chaque exécution émet un événement de gouvernance (ds.history()).

② stage()édition staged : branche Iceberg · manifeste · version pending

veto ⇒ néantAuditVeto : l'édition staged n'existe pour personne — rien à nettoyer

9 EL — les sources de données comme nœuds de flow code & no-code

Le « E+L » de l'ELT : récurrent, incrémental, rejouable — déclaré en code (source()/@source) ou généré par l'assistant no-code (écrans S8/S9), un seul objet compilé.

L'état (curseurs) vit dans le Postgres de Flows par (source, stream, env) · backfill = rejouer une plage de curseur → éditions dédiées · le même objet est édité en code (repo) ou en no-code (S8/S9) — un seul manifeste compilé.

Le vrai sujet n'est pas « importer un existant » : c'est l'Extract-Load récurrent — brancher des systèmes sources (bases, API, SFTP, topics) et les faire atterrir en datasets gouvernés de façon répétée, incrémentale et rejouable. Hemera n'a pas de service d'ingestion séparé : une source est un nœud SOURCE d'un flow — même manifeste, même plan/apply, mêmes workers (tag el), même garde WAP, même lignage. L'anatomie : une source = un connecteur + un secret (référence, résolue par le worker) + des streams découverts (discover() : tables, endpoints, dossiers) ; chaque stream sélectionné produit un dataset d'atterrissage, et chaque run de sync produit une édition estampillée origin.system/uri/cursor/fetched_at.

Quatre étages de connecteurs, un seul contrat : ① catalogue natif (PG, MySQL, MSSQL, Oracle, BigQuery, Snowflake, S3/SFTP, Google Sheets, REST paginé, Jira, HubSpot…) — chaque connecteur publie une spec (config en JSON Schema + discover()), c'est elle qui génère les formulaires du no-code ; ② dlt embarqué (Apache 2.0, verified sources) — dlt fait le E, le lake fait le L (WAP), wrappé en @source ; ③ OLake wrappé (Apache 2.0, Go) pour la haute volumétrie DB : full chunké + CDC log-based — piloté par le même manifeste, étudié et validé au banc dans le document ⑥ ; ④ Python libre (@source) pour tout le reste. Dans les trois cas le runtime fait le Load : vous ne touchez jamais l'écriture Iceberg, vous yieldez des enregistrements.

10 Faire entrer un existant — le one-shot : adoption, modèles, bootstrap

Distinct de l'EL récurrent : le geste unique — adopter une table Iceberg déjà là, importer un modèle, amorcer un store vectoriel — avec une provenance d'origine honnête.

À côté de l'EL récurrent (§9), il reste le geste one-shot : adopter une table Iceberg déjà là, importer un modèle depuis MLflow, amorcer un store vectoriel. Les points durs des kinds étendus — dits honnêtement

Les points durs, dits honnêtement (révisés avec les services) : ① GC des blobs — transféré au service files, qui purge par refcount depuis les snapshots vivants de l'index (fournis par le Catalog) : plus de croisement fragile dans un flow de maintenance, mais un contrat Catalog↔files à tester (FS-2) ; ② signature par fichier — résolu par conception : le service files presigne, après la même décision OpenFGA sur la table d'index — INT-15 devient un test du service, plus une inconnue Lakekeeper ; ③ volumétrie du lignage fichier — lignage par content_hash en arêtes agrégées (fichier→fichier), pas ligne-à-ligne ; ④ EXPORT/STREAM sans WAP — assumé et affiché : flux et caches ne sont pas des états versionnés, leur vérité reste l'édition source ; ⑤ workers gpu = un tag de plus dans la file, mais l'image et l'autoscale gpu sont un chantier ops réel ; ⑥ authz Kafka — pour le kind STREAM, aligner les ACL topics sur OpenFGA (bridge à instruire) sinon l'authz du flux reste plus faible que celle des datasets.

Hemera — document ② : le modèle de développement (objets · syntaxe · EL · interop). Tranche D1 (revue d'intégration §6) · complète l'architecture v2 (§13–14) et l'annexe schéma.
