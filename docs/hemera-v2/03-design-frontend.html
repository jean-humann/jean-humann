S0 Principes de design & modèle de navigation

Cinq règles qui structurent chaque écran — puis le shell applicatif commun.

🗂️
Catalog-first

La porte d'entrée n'est pas « mes jobs », c'est la donnée. Tout écran mène à une fiche dataset, et toute fiche dataset mène aux flows qui la produisent/consomment. La recherche globale (⌘K) cherche datasets, flows, runs, colonnes.

🛡️
Gouverné par construction

L'UI n'a pas d'état « non sécurisé » : chaque aperçu, requête ou export passe par l'identité OIDC de l'utilisateur → Lakekeeper. Ce qu'on n'a pas le droit de lire n'est pas grisé mystérieusement : l'écran dit pourquoi et offre « demander l'accès ».

🧬
La provenance est un lien

Chaque nombre affiché est cliquable vers sa preuve : une édition → son run → son code (git ref) → ses entrées épinglées. Badge d'audit, snapshot, veto : tout navigue.

🖼️
Une surface, trois publics

No-code (canvas), code (repo), SQL (modèles) sont des projections du même DAG : le canvas montre les nœuds code/SQL en lecture seule (opaques mais présents), jamais deux vérités.

🌿
L'environnement est global

Le sélecteur d'environnement (= branche Iceberg) est dans la barre du haut et re-contextualise tout : aperçus, runs, lignage, qualité. prod et dev ne se mélangent jamais silencieusement.

📡
Temps réel sobre

Les états de runs/jobs arrivent en SSE/WebSocket (file Postgres → API). Pas de spinner-roulette : les transitions d'état (QUEUED→RUNNING→…) s'affichent là où elles se produisent, dans le DAG.

◆ Les trois chemins d'un run — IDE local · frontend · API

Un seul modèle de run, deux plans d'exécution. Ce qui change entre les surfaces, c'est qui orchestre et quel code tourne — jamais la gouvernance.
