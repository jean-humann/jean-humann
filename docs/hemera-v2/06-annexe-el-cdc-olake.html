1 Pourquoi OLake, et la méthode

Le §9 du document ② définit le modèle EL (sources = nœuds de flow, éditions, curseurs). Cette annexe le confronte au meilleur moteur open-source du moment pour en durcir l'exécution.

OLake (datazip-inc/olake, Apache 2.0, Go) est un moteur d'ingestion spécialisé : réplication full + CDC de PostgreSQL, MySQL, MongoDB, Oracle, DB2, MSSQL, Kafka et S3 vers Iceberg (catalogues REST/Glue/Hive/JDBC) ou Parquet — throughput annoncé 580 k lignes/s (PG). Architecture : un binaire Go par driver (protocole spec / check / discover / sync, façon Airbyte mais sans conteneur par connecteur), et pour Iceberg un sidecar Java piloté en gRPC (écritures Arrow, equality deletes). C'est exactement le périmètre où notre étage « natif Python » sera court : gros backfills parallèles et CDC log-based.

Méthode : ① lecture dirigée du code (fichiers cités fait par fait) ; ② banc S7 exécuté ici — build Go du driver Postgres, cluster PG 16 local passé en wal_level=logical, publication + slot pgoutput, deux syncs réels, inspection des Parquet produits. Aucun fait ci-dessous n'est déclaratif : chaque ligne est soit du code cité, soit un comportement observé.

4 Le design EL v2 — sept améliorations pour les steps de flow

Ce qu'on adopte d'OLake, ce que notre modèle d'éditions ajoute, et où chaque garantie s'applique.

⏱️
A · CDC = runs bornés → éditions

Adopté tel quel (E5) : un sync CDC capture sa cible WAL et s'arrête — c'est un job, pas un démon. Chez nous : chaque run = une édition de la table d'atterrissage estampillée origin.cursor = {lsn_from, lsn_to}. Cadence = refresh de la source (ex. @5m), garde de retard = lag du slot. La file SKIP LOCKED, les leases et les retries s'appliquent sans rien inventer.

🎯
B · Exactly-once généralisé : le curseur vit dans l'édition

Adopté et renforcé (E7/E8) : le curseur de vérité = snapshot properties de la dernière édition publiée ; le state du Postgres de Flows n'est qu'un cache. Recovery = replay borné jusqu'au curseur ancré, épinglé exactement. L'ack du slot vient après le publish — jamais l'inverse.

🪓
C · Backfill chunké = jobs de la file

Adopté (E2/E3/E4) : GetOrSplitChunks (CTID ou PK) → N jobs avec lease/retry ; idempotence par chunk-ID relue depuis l'édition staged. Fenêtre de chevauchement backfill/CDC reprise telle quelle (E6) : colonnes _hemera.op (r/c/i/u/d), _hemera.cdc_lsn, _hemera.row_id sur les tables d'atterrissage CDC.

🌿
D · WAP × CDC — la frontière à trancher

OLake écrit sur la table finale ; nous voulons la garde d'audits. Cible : atterrissage sur branche staging via le catalogue REST (Lakekeeper) puis audits → fast-forward — à vérifier dans le writer Java (support du branch ref) : ticket EL-4. Repli assumé : régime « STREAM » (audits post-publication sur la landing), déjà acté pour les flux.

🧩
E · Le moteur d'extraction devient un étage de plus

Même grille que dbt : outil tiers = exécuteur encapsulé, garanties à la frontière. Étages : ① natif Python (API/fichiers légers) · ② dlt (long tail) · ③ OLake wrappé = haute volumétrie DB full+CDC (binaire Go + sidecar Java sur workers el-cdc, piloté par le MÊME manifeste source()) · ④ @source custom. Le choix d'étage est un placement, pas une API différente.

🧬
F · Dérive de schéma CDC sous policy

OLake évolue le schéma côté writer, sans garde. Chez nous la dérive DDL amont (colonne ajoutée, type changé) passe par la policy du §9 : additive="apply" (expansion auto, règles R de l'annexe ④) · breaking="quarantine" (run bloqué + alerte S8). Ticket EL-8 : mapper les messages relation de pgoutput sur cette policy.

🛰️
G · Kafka : le 2PC qu'OLake n'a pas, notre édition le donne

OLake Kafka est at-least-once (E11 — « TODO: hard »). Notre modèle le résout par construction : ① poll → ② publier l'édition avec [offset_from, offset_to] dans ses snapshot properties → ③ commit du consumer group (advisory). Crash entre ② et ③ ⇒ relecture, dédupliquée par la plage déjà publiée. Le commit d'offset n'est plus jamais la vérité.

Exactly-once Hemera — le même patron pour DB et streamsrun borné → écritures sur staging → audits → publish (édition estampillée du curseur : LSN range ou offset range) → ack source (slot / consumer group) EN DERNIER
Crash avant publishrien n'existe (WAP) · re-run depuis le curseur de la dernière édition · chunks déjà commités sautés
Crash entre publish et ackrecovery borné : rejouer jusqu'au curseur de l'édition, dédup par plage · puis ack — jamais de doublon, jamais de trou
Une seule règle mémorisable : la source n'est acquittée qu'après la publication de l'édition qui la couvre — le reste (recovery, dédup, reprise) en découle mécaniquement.
« Mais alors, le worker CDC/Kafka doit tourner h24 ? » — Non, et c'est le point. Entre deux runs, rien ne se perd : côté Postgres le slot logique retient le WAL sur le serveur source tant qu'il n'est pas acquitté ; côté Kafka le broker retient les messages (rétention du topic) et la plage publiée dans l'édition fait foi. Ce qui doit être h24, c'est ce qui l'est déjà : le scheduler Flows et le pool partagé de workers (autoscalé) — mais aucun process dédié par source, contrairement au modèle Debezium/Kafka Connect (une task permanente par connecteur). Les workers sont fongibles : n'importe quel el-cdc peut prendre le prochain run puisque le curseur vit dans l'édition, pas en mémoire. Les deux vraies contraintes : ① la cadence doit tenir le lag — slot en retard = WAL accumulé = disque du serveur source (métrique S8, EL-6) ; côté Kafka, cadence < rétention du topic ; ② la latence = la cadence : c'est du micro-batch (@1m–@5m réaliste), cohérent avec un modèle où la vérité est une édition publiée, pas un flux continu. Si un cas exige mieux : mode continu = boucle de runs bornés sous un même lease (chaque itération publie son édition, le crash reste trivial ; initial_wait_time réglé court) — une optimisation de placement, pas un changement d'architecture.

5 Industrie 4.0 — brancher l'usine : OPC UA, MQTT/Sparkplug, historians

Les flux d'usine ne ressemblent ni à un WAL ni à un topic Kafka — mais le contrat d'édition s'applique dès qu'on leur donne ce qui leur manque : un journal rejouable.

📜
R-IoT-1 · Pas de gouvernance sans journal rejouable

MQTT est un transport, pas une vérité : QoS 1/2 garantit la livraison, pas la relecture (un retained message n'est pas un historique). Toute voie MQTT/OPC UA-subscription passe par un étage durable (Kafka / JetStream, alimenté par le pont du broker) avant l'atterrissage gouverné — l'édition redevient alors une plage d'offsets, comme partout. Même règle, même recovery, même exactly-once qu'au §4.

⏰
R-IoT-2 · Éditions = fenêtres de temps + watermark

Les usines produisent du retard structurel : store-and-forward des passerelles, liens coupés, horloges edge décalées. Une édition d'atterrissage = fenêtre [t_from, t_to] + watermark ; la donnée tardive arrive en édition de rattrapage dédupliquée par (tag_id, ts, seq) (le seq Sparkplug sert exactement à ça) — jamais de réécriture silencieuse, l'audit de complétude dit ce qui manque.

🏷️
R-IoT-3 · La forme d'atterrissage : table longue + qualité

Schéma EAV canonique : ts · tag_id · value · quality + hiérarchie ISA-95 (site/ligne/cellule) en colonnes et en labels Catalog. Partition temps + bucket de tags. Les codes qualité OPC UA sont une colonne auditée (taux de bonne qualité ≥ seuil, complétude des tags attendus par fenêtre) — le veto WAP s'applique aux capteurs comme aux commandes.

🎛️
R-IoT-4 · Positionnement honnête : analytique, pas contrôle

Hemera ingère l'usine pour l'analytique gouvernée : maintenance prédictive, analyse qualité, traçabilité réglementaire, features du jumeau numérique — en micro-batch (fenêtres 1 s agrégées → rollups INCREMENTAL, du T ordinaire). Le temps réel de contrôle/alerte (< 1 s) reste au niveau UNS/SCADA : on consomme l'UNS, on ne le remplace pas.

L'invariant qui rend tout gérable : quel que soit le type, c'est le même cycle ⓪–⑤ (curseur ← dernière édition · extract borné · staging+dédup · publish avec la plage · ack · lignage) exécuté par les mêmes workers fongibles — un type de flux se déclare entièrement par son quadruplet (journal, plage, clé de dédup, ack) plus un watermark pour les flux temporels. C'est ce que le manifeste encode déjà (mode, dedup_keys, watermark ; l'ack est impliqué par le connecteur). Corollaires : ① un flux de Classe B n'est jamais branché en direct sur la gouvernance — on lui donne d'abord un journal ; ② les subscriptions OPC UA gagnent un filet unique : une déconnexion (NDEATH) déclenche un backfill HDA de la fenêtre manquée — le trou se répare par le chemin batch. 6 Le code — manifeste, moteurs, Kafka exactly-once

La déclaration du §9 (document ②) ne change pas — le moteur devient un choix de placement, le CDC un mode de stream.

# ── La même source(), avec l'étage moteur et le mode cdc ─────────────────────
crm = source("crm", connector="postgresql", secret="CRM_DB",
             engine="olake",                        # ① natif · ② dlt · ③ olake (volumétrie / CDC) · ④ custom
             refresh="@5m")
crm.stream("public.orders", output="crm.orders", mode="cdc",
           chunk_column="order_id",                 # backfill parallèle par plages de PK (sinon CTID)
           replica_identity="full")                 # exigé au setup (E13) — sinon quarantaine
crm.on_schema_drift(additive="apply", breaking="quarantine")

# ── Ce que le worker el-cdc exécute (wrap OLake — garanties à la frontière) ──
# 1. curseur ← snapshot properties de la DERNIÈRE édition publiée (pas le state file)
# 2. olake sync --config … --state <reconstruit>    # backfill chunké repris + WAL replay borné
# 3. atterrissage staging (catalogue REST Lakekeeper) → audits → publish
# 4. édition estampillée origin.cursor={lsn_from,lsn_to} · ack du slot APRÈS le publish

# ── La table d'atterrissage CDC — lisible telle quelle, ou en vue « état courant » ──
lake.sql("""
  CREATE VIEW crm.orders_current AS            -- dernière version de chaque ligne, deletes exclus
  SELECT * EXCLUDE (_hemera_op, _hemera_cdc_lsn) FROM crm.orders
  QUALIFY row_number() OVER (PARTITION BY order_id ORDER BY _hemera_cdc_lsn DESC) = 1
    AND _hemera_op != 'd'
""")
