3 Couture B · Orchestrateur ⇄ file Postgres I12 exécuté — PostgreSQL 16 réel

La table flow_job exacte de l'architecture, 3 workers concurrents, un crash simulé.

Schéma de l'architecture §14 monté tel quel (états, depends_on, lease TTL, deps_done() en SQL). Scénario : DAG source_a + source_b → transform → output, plus un nœud indépendant ; 3 workers concurrents ; le worker w0 crashe en tenant source_b (abandon sans commit).

Résultat vérifié : aucun doublon d'exécution (le SKIP LOCKED distribue sans collision) ; le job du worker mort est re-loué après expiration du lease (attempt=2) et terminé par un autre worker ; transform n'a démarré qu'après ses deux dépendances, output après transform ; tous les jobs finissent SUCCEEDED, en 2,3 s murales. La revendication anti-zombie « un seul registre, lease à TTL » tient exactement comme spécifiée.

Réserves d'exploitation (aucune ne change le design) : ① la re-location attend l'expiration du lease → le TTL est un compromis latence-de-reprise / faux-positifs (heartbeat qui prolonge, TTL court 30–60 s) ; ② deps_done() en sous-requête est O(deps) — indexer (state) et (tag, state) ; ③ le polling à vide se règle par LISTEN/NOTIFY Postgres (réveil des workers à l'enqueue) plutôt qu'en réduisant l'intervalle ; ④ prévoir l'autovacuum : la table est à fort churn → fillfactor réduit + partitionnement par âge des runs terminés.

4 Couture C · lake ⇄ Iceberg : concurrence du WAP I1–I5 exécutés

Ce qui se passe quand deux runs touchent la même table — les deux correctifs qui en sortent.

TestRésultat vérifiéConséquence
I1 · Deux appends concurrents (handles obsolètes)2ᵉ commit rejeté (« branch main was created concurrently ») — PyIceberg ne fait aucun retry automatique (contrairement au client Java)correctif 1 : lake implémente retry-refresh-reapply sur CommitFailedException (borné, backoff)
I2 · Deux publications WAP concurrentes sur la même tablele verrou optimiste du catalogue a rejeté le perdant (A FAILED, B PUBLISHED, zéro perte) — mais un publish par set_current_snapshot aveugle peut pointer main sur une lignée qui ne contient pas la publication concurrente : perte silencieuse possible selon l'ordrecorrectif 2 : le publish vérifie l'ascendance (la tête d'env doit être ancêtre de la tête wap), sinon abort + re-run du WAP depuis la nouvelle tête ; et la sérialisation par dataset dans l'orchestrateur (déjà au design) devient une exigence, pas une optimisation
I3 · Branche env_dev quand main avancela branche est un pointeur figé (1 ligne vs 2 sur main) — pas un overlayconfirme le design : le fallback dev→prod est par table (table non reconstruite en dev = lire main), jamais intra-table
I4 · snapshot_properties sur upsert+brancheprovenance présente sur le snapshot de mergela provenance (§20 archi) couvre bien les publications incrémentales

# le publish corrigé (remplace le set_current_snapshot naïf du prototype cleyrop-dm)
def publish(tbl, env_branch, wap_branch):
    tbl.refresh()
    env_head, wap_head = tbl.snapshot_by_name(env_branch), tbl.snapshot_by_name(wap_branch)
    if not is_ancestor(tbl, ancestor=env_head, of=wap_head):        # qqn a publié entre-temps
        raise StaleWapError("re-run WAP from new head")             # le job repart en QUEUED (idempotent)
    fast_forward(tbl, env_branch, to=wap_head)                      # + retry-refresh sur CommitFailedException

5 Couture D · SQL multi-moteurs & lignage colonne I6–I8 exécutés

Le contrat « même SQL sur DuckDB et Spark » et la promesse du lignage par AST, tous deux exercés.

🔁
I6 · Transpilation spark ⇄ duckdb

SQLGlot 30 transpile correctement les constructions réelles testées : date_trunc, explode→UNNEST, collect_list→ARRAY_AGG FILTER, unix_timestamp→EPOCH(STRPTIME), QUALIFY, try_divide→CASE. Le gateway dev (DuckDB) peut exécuter les modèles écrits en dialecte spark.

🧬
I7 · Lignage colonne par AST

sqlglot.lineage() remonte correctement amount_eur ← raw_orders.amount + fx.rate à travers CTE + jointures, avec schémas fournis. Nuance : les feuilles sortent au niveau alias (cu.region) — qualifier la requête d'abord (sqlglot.optimizer.qualify) pour des noms pleinement résolus. LN-3 est faisable tel que spécifié.

⚠️
I8 · Les divergences sont sémantiques, pas syntaxiques

substr(x, 0, n), division entière, comportements NULL : la transpilation est correcte mais les moteurs divergent sur les bords. → Politique : dialecte source unique (spark), et une suite golden (mêmes requêtes, mêmes données, résultats comparés DuckDB vs Spark Connect) comme gate E3 — le run local « comme en prod » en dépend.

📦
I9 · cloudpickle

Closure + globals capturées, désérialisées et exécutées dans un autre process (3.1.2, Python 3.11). L'invariant reste la même version mineure de Python des deux côtés — épinglée par l'image (3.11.x partout).

6 Couture E · SQLMesh ⇄ Flows — la tension à trancher décision D1

Le seul recouvrement structurel du design : deux systèmes veulent posséder l'état et les environnements.

Le problème, précisément. SQLMesh apporte quatre choses : ① parsing/rendu SQL multi-dialectes (SQLGlot), ② calcul incrémental par fenêtre temporelle (@start_ds/@end_ds, intervalles suivis), ③ audits bloquants, ④ son orchestration : fingerprints, state DB, environnements virtuels par vues, plan/apply. Or Hemera v2 possède déjà ③ (audits WAP, plus forts : pré-publication), ④ (fingerprints Flows, environnements = branches Iceberg, plan/apply, file de jobs). Utiliser SQLMesh « entier » en mode intégration = deux state stores, deux notions d'environnement, deux plans — le ticket WK-4b (« raccorder les envs virtuels SQLMesh aux branches ») sous-estime ce recouvrement : la couche virtuelle de SQLMesh (vues + tables hash-nommées) n'a pas de point d'extension officiel « remplacez mes vues par des branches Iceberg ».

OptionCe que fait SQLMeshCe que fait FlowsVerdict
D1-a · SQLMesh entier (lib) + envs raccordés aux branchesstate, plan, envs virtuels, exécution SQLorchestration des nœuds non-SQLrecouvrement maximal · point d'extension inexistant · deux vérités — déconseillé
D1-b · SQLMesh = compilateur SQL (recommandé)parse/rendu dialecte, macros, calcul de fenêtre incrémentale, définitions d'audits — en bibliothèque, sans state ni envsfingerprints, branches, WAP, audits exécutés sur la branche wap, matérialisation via lakeun seul état, une seule notion d'env · SQLMesh reste remplaçable (le prototype cleyrop-dm prouve le cœur en SQLGlot pur)
D1-c · Wrap (projet SQLMesh/dbt importé)tout, dans son sous-univers (schémas dédiés, son state)orchestre la région comme une boîte : trigger, attente, lecture des sortiesOK tel quel — les garanties Hemera (WAP, provenance) s'appliquent à la frontière de la région, pas à l'intérieur — à documenter honnêtement
Recommandation D1-b : en mode intégration, SQLMesh est un moteur de rendu et de fenêtrage, pas un orchestrateur : Flows lui demande « rends-moi le SQL de ce modèle pour l'intervalle [start, end) », exécute le résultat via le gateway (Spark Connect/DuckDB), et matérialise via lake sous WAP. Les audits déclarés dans MODEL() sont lus par le compilateur et exécutés par notre garde WAP. Ça préserve la syntaxe SQLMesh/dbt pour les utilisateurs (la promesse du §16 archi) sans payer la double orchestration. Gate E3 : un POC de 2 jours valide que l'API bibliothèque de SQLMesh expose bien rendu + intervalles sans initialiser son state ; sinon, repli SQLGlot-only (perte : macros SQLMesh et fenêtrage automatique — recodé dans le compilateur, ~1 semaine).

8 Couture G · Opérateur Spark · workers · Kafka · Trino revue sur pièces

Les composants d'infrastructure, avec les points précis à valider en environnement réel.

☸️
Opérateur Spark K8s — serveur Connect long-vivant

La CR SparkApplication vise des jobs ; un serveur Connect est un service. À valider : politique de restart (Always), Service stable sur 15002 + readiness, budget de disruption, et surtout dynamic allocation sans external shuffle service → spark.dynamicAllocation.shuffleTracking.enabled=true obligatoire sur K8s. Vérifier l'artefact iceberg-spark-runtime-4.1_2.13 (Iceberg 1.11) avant de figer l'image. Alternative si l'opérateur Apache coince : Deployment Helm simple — le serveur Connect n'exige pas d'opérateur.

🔎
Trino — l'identité s'arrête à la porte (D2)

Trino s'authentifie lui-même auprès de Lakekeeper (credential de catalogue statique) : par défaut, tous les utilisateurs Trino deviennent une seule identité côté données — la politique OpenFGA par utilisateur ne s'applique plus. Options : ① Trino = identité de service lecture seule avec un périmètre réduit + authz par OPA côté Trino (deux systèmes de politique — dérive) ; ② passthrough des credentials utilisateur (« extra credentials » / catalogues par utilisateur — lourd) ; ③ restreindre Trino aux datasets non sensibles tant que ①/② non tranchés. Décision D2 requise avant d'ouvrir Trino en libre-service.

🛡️
Isolation worker — nsjail n'est pas gratuit (D3)

nsjail exige des privilèges kernel (namespaces, seccomp) que les PSS « restricted » de K8s refusent. Options : ① pods privileged dédiés aux workers (simple, à isoler par node pool) ; ② gVisor/kata en RuntimeClass (isolation forte, pas de privilège dans le pod) ; ③ un pod éphémère par job (l'isolation par K8s lui-même — plus lent, plus simple). Décision D3 = arbitrage sécurité/latence ; le design (un job = un process isolé) survit aux trois.

📨
Kafka — règles de flux pour Catalog & lignage

Clé de partition = identifiant de table (ordre garanti par table) ; consommation idempotente par clé naturelle (snapshot_id pour les événements de données, run_id+node pour OpenLineage) ; rétention longue sur lineage-events (c'est la source de rejeu du Catalog event-sourcé) ; schémas d'événements versionnés (le socle protobuf existe, OpenLineage est JSON — les deux cohabitent, pas de registry à inventer en v1).

🐍
Workers — l'outillage vérifié ici

uv 0.8 présent et fonctionnel (le venv Spark de cette revue a été construit avec) ; pyspark-client 4.1.2 disponible sur PyPI pour l'image légère ; cloudpickle 3.1 OK ; Python épinglé 3.11.x. Le pattern « cache uv + dedicated workers » ne présente pas de risque technique.

🗄️
Le reste du socle

Postgres 16 : file validée (I12) + state Flows + Catalog — un seul moteur de base à exploiter. Keycloak/Kafka/MinIO : déjà en production chez Hemera, pas de nouveau risque. Frontend React Flow : aucun couplage nouveau (client des API).
